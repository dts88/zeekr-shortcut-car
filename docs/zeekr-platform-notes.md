# 极氪 App Lab 平台事实笔记

这份文档记录本项目开发过程中掌握的**极氪车机平台事实**：视频流格式、车机逻辑、
资源限制、以及踩过/绕过的坑。目的是让后续开发不必重新摸索。

**大部分事实来源于 [openavm-recorder](https://github.com/Dantenothing/openavm-recorder)
项目公开的 README 与源码注释**（作者 Dantenothing，保留所有权利）。这些是对车机行为的
事实性观测记录，不是代码。本项目未复制其任何源代码。**在此致谢原作者把这些观测公开出来——
没有它们，下面每一条都要拿真车去撞一遍。**

标注说明：
- 【实测】= 上游项目在真车上观测到的结果
- 【未知】= 尚未确认，不要当成事实用
- 【本项目】= 本项目据此做出的设计决定

## 1. 视频流

### 1.1 只有一路合成流，不是四个摄像头

【实测】App Lab 环境下，第三方应用通过标准 Android Camera2 拿到的是
**一路已经处理好的合成流**，不是四路独立摄像头，也无法请求四个独立的相机设备。

### 1.2 尺寸与排布

| 排布 | 尺寸 | 构成 |
|------|------|------|
| 竖排（实测车机给的就是这个） | `1280×5140` | 四个 1280×1280 方形画面竖向堆叠 + 5 条 4px 分隔带 |
| 横排 | `5120×1280` | 四个 1280×1280 横向排列，`5120 = 4×1280`，无分隔带 |

竖排的算法：`5140 − 4×1280 = 20`，均分给 5 条分隔带（上边缘、三条内部分隔、下边缘），
每条 4px。分隔带在画面上表现为细线。

【本项目】`CompositeStreamGeometry` 按此实现，并在排布对不上时安全回退为四等分。

### 1.3 HAL 可能给一个压扁的小尺寸提示

【实测】车机 HAL 有时只声明一个较小的 Surface 提示尺寸（例如 `640×480` 附近），
但内部送来的**仍是同一份四联合成内容**，只是被压扁了。

上游的做法是：预览优先选择最接近 `640×480` 的普通声明尺寸作为稳定回退，
只有当 SurfaceTexture 明确声明了 `1280×5140` 时才请求那个大缓冲区。

【本项目】拆分几何一律按**合成流真实尺寸**计算，得到归一化窗口后再套到实际绘制区域。
这样缓冲区无论多大、是否被压扁，四个画面的位置与比例都正确。
`FourLaneContainer.setSourceSize()` 会忽略"不像合成流"的尺寸，避免把已探测到的正确几何降级。

### 1.4 绝不要臆造分辨率

【实测】上游明确的工程原则：只使用 HAL **实际声明**的尺寸，不做近似替换、不做隐式回退。
拿一个没被声明的尺寸去开相机，结果是黑屏或直接失败。

【本项目】`ZeekrCompositeProfile` 遵循同样的原则，一个候选都没有时返回"未找到"，
由界面明确提示用户，而不是硬开。

### 1.5 编码参数

【实测】整条合成流的实际录制表现：

- 编码码率约 **28 Mbps** @ `1280×5140`
- 落盘速度约 **200 MB/min**，即 **3–4 MB/s** 持续写入
- 一小时录制约产生 **12 GB** 主机层写入量（还没算文件系统与闪存写放大）

## 2. 渲染：一个必须避开的坑

### 2.1 用 GL 自建 SurfaceTexture 顶替生产者会崩溃

【实测】**这是本项目最重要的一条平台事实。**

直觉上最优雅的做法是：在 GL 线程建一个外部纹理（OES），把它的 SurfaceTexture 交给
Camera2，然后用着色器把四个画面渲染成四宫格。**这条路在真车上崩了。**

上游源码注释原文：

> "The old automatic preview crashed because it replaced the working producer with a
> GL-owned SurfaceTexture. The current path has been verified on the car: Camera2 feeds
> one ordinary TextureView and its parent redraws that same child into four cells."

### 2.2 验证可行的结构

```
Camera2 ──写入──> 一个普通的 TextureView（唯一的相机消费者，不被改造）
                        │
                        │ 父容器把同一个子视图重复画 4 次，
                        │ 每次裁剪到一个格子并映射对应的源矩形
                        ▼
                   2x2 四宫格
```

关键在于**相机链路一点都不动**，只改变"这个已经在正常工作的子视图怎么被画出来"。

【本项目】`FourLaneContainer` 采用这套结构。本项目最初写的是 GL 方案，
读到上游这条注释后**整体推翻重写**——这正是读代码学事实的价值。

## 3. 车机逻辑

### 3.1 相机所有权：原厂功能优先

【实测】原厂车辆软件可能随时接管相机资源，用于：

- 原厂 360° 环视
- 倒车影像
- 泊车辅助相机功能
- 其他 OEM 相机接口

应用**必须让路**。当 Android 报告相机不可用或已被占用时，正确做法是：

1. 停止或暂停录制；
2. 让原厂功能保有相机；
3. 只在原厂功能释放之后再重试。

**第三方应用永远不能被视为优先于原厂车辆功能。**

【本项目】EVCam 基座自带 `CameraRecoveryStateMachine` 式的重建与退避逻辑；
后续应针对极氪补一条"确认被原厂接管时不要抢"的策略。**这是当前待办项。**

### 3.2 App Lab 存在资源管理策略

【实测】App Lab 界面自身的提示：

- **体积过大的应用可能无法启动**；
- App Lab 应用在车机其他功能高负载时**可能被降速**。

【未知】具体的 CPU/GPU/RAM/存储 I/O 限制、调度优先级、是动态还是固定、
哪些原厂负载优先——全部未公开、未验证。

【本项目】APK 体积是一个真实风险。初始构建 **24.4 MB**，其中 21.5 MB 是 dex。
已裁掉用不到的模块与依赖后降到 **约 16 MB**（-34%）：

| 移除 | 依赖 | 收益 |
|------|------|------|
| 远程查看（钉钉/飞书/Telegram/心跳）、推流、扫码互传 | DingTalk SDK、NanoHTTPD、ZXing | 24.4 → 19.6 MB |
| VHAL 车辆信号（换成空实现） | gRPC ×2 + 原生 .so | 19.6 → 16.0 MB |

若仍需继续压缩，下一步顺序：
① 整体移除补盲模块（还能带走 `assets/douyin*` 共 0.84 MB，但它与
`CameraRecordingService`、`MainFloatingWindowView` 耦合，需小心）；
② 开启 R8（`isMinifyEnabled = true`）+ 资源裁剪——Gson/Glide 用反射，
必须配 keep 规则并**实机回归**，不要盲发。

### 3.3 内存

【实测】录制过程中车机系统报告约 **9 GB 可用 RAM**。
这只是系统自报值，说明该工况下没有明显内存压力，
但不构成对内存带宽、分配延迟等共享资源的度量。

### 3.4 实测路试

【实测】截至 2026-08-12，上游累计约 **4 小时实车路试**，
条件为：后台持续录制 + Android Auto 同时正常运行 + 正常用车。

期间未观察到：录制失败、明显卡顿/丢录、Android Auto 异常、
原厂 360° 相机异常、车辆异常、车机故障。

这是有用的经验证据，但**不构成长期安全性、零资源开销或普适兼容性的证明**。

### 3.5 一次与本应用无关的车机中断

【实测】在**任何第三方 App Lab 应用安装之前**，测试车曾出现过一次完整的车机中断：
中控黑屏、HUD 同时不可用、持续约两分钟后自行恢复，期间基本驾驶功能未受影响。

这条只作为测试背景记录，既不能说明原因，也**不能证明第三方应用永远不会引发类似问题**。

## 4. 存储

### 4.1 U 盘写入——上游的观察在本项目不成立

上游 README 记录：

> "The tested App Lab environment does not currently allow AVM Recorder to write
> recordings directly to external USB storage."

【本项目实测】**这条不适用于本项目。** 本项目作者已在极氪车机上安装 EVCam，
并**成功把录像写入外置 U 盘**。这是第一手实测结果，优先级高于上游在其自身应用中的观察。

两者不一致的可能原因（均未验证）：车机固件/App Lab 版本不同；
两个应用请求外置存储的方式不同（EVCam 走 `getExternalFilesDirs()` 的第二个卷
并写入 U 盘公共目录）；或该限制只在特定条件下出现。

【本项目】**U 盘存储按可用对待**，直接沿用 EVCam 的实现（`StorageHelper` 及相关逻辑），
不做删改。这也是选 EVCam 做基座的核心理由之一。

> 这条是一个有用的提醒：上游记录的是**它自己那个应用**在**它那台车**上的观察结果，
> 不等于平台的硬性限制。凡是能自己实测的，以实测为准。

### 4.2 闪存写入量

【实测】自动清理只控制"占用空间"，不减少"累计写入量"。
删旧片段再写新片段，占用可以基本恒定，但底层 NAND/UFS/eMMC 的写入是持续累加的。

按 200 MB/min 算，一小时约 12 GB 主机层写入。

【未知】车机内部存储的器件型号、NAND 类型、耐久度评级、预留空间、
磨损均衡策略、文件系统写放大、寿命写入计数器——全部未知。

**内部闪存耐久性因此是一个未解决的风险。**

【本项目】上游给出的工程建议值得照做：
**避免不必要的临时文件与中间落盘，尽量在内存中处理，只持久化最终编码结果。**

既然 U 盘可写（见 4.1），最省心的做法是**直接录到 U 盘**，
车机内部闪存就完全不承担这份写入量。EVCam 的"中转写入"（先写内部再异步搬到 U 盘）
会让写入量翻倍，只在 U 盘写入不稳时才值得开启，默认建议关闭。

## 4.5 性能：预览与录制共用同一个分辨率（已知瓶颈）

【本项目】EVCam 的相机管线里，**预览和录制用的是同一个 `previewSize`**：
`MultiCameraManager` 直接拿 `camera.getPreviewSize()` 去配置 MediaRecorder
（见 `MultiCameraManager` 中 `Size previewSize = camera.getPreviewSize();`
后面紧跟着算码率、设录制参数）。

在极氪合成流场景下，这意味着：想录到完整的 `1280x5140`，**预览也必须跑在 6.55 MP**。
代价是每一帧都要把一张 6.55 MP 的纹理送去显示，而 `FourLaneContainer` 还要把它
**画四次**（四宫格）——实际显示区域可能只有 1000x600 左右。这是本项目当前最明显的
GPU / 内存带宽浪费。

【实测参考】上游 openavm-recorder 是把两者**分开**的：预览优先选最接近 `640x480`
的普通声明尺寸作为稳定回退，只有确实需要时才请求 `1280x5140` 的大缓冲区（见 1.3）。
同一份合成内容被压扁进小缓冲区，归一化拆分照样正确。

【已实现，默认关闭】设置里新增开关 **「预览用低分辨率（实验性）」**：
开启后 `SingleCamera` 会为预览缓冲区单独挑一个接近 `640x480` 的**已声明**尺寸
（`choosePreviewBufferSize()`），录制仍用完整的 `previewSize`，MediaRecorder 配置不变。
四宫格拆分不受影响——它用的是归一化坐标，缓冲区被压扁也算得对。

挑不到合适的小尺寸就自动退回录制尺寸，绝不臆造未声明的分辨率。

**默认关闭**，因为能否生效取决于车机 HAL 是否支持「预览小、录制大」这种流组合。
开启后请确认：预览画面正常、录制文件仍是完整分辨率、且录制不中断。

> 注意：语言层面（Java / Kotlin）在这里**不是**瓶颈。两者编译到同一份 DEX、
> 跑在同一个 ART 运行时。真正的开销在相机取流、硬件编码、GPU 合成与存储 I/O。

## 4.6 补盲模块：保留，待实车验证

补盲（BlindSpot）是 EVCam 里一套**吉利银河车型专用**的驾驶辅助功能，与记录仪主功能独立：
**收到信号 → 自动弹出对应侧摄像头画面**。

| 触发 | 动作 |
|------|------|
| 打左/右转向灯 | 弹出该侧画面，看变道盲区 |
| 开车门 | 弹出该侧画面，避免开门碰到后方来车 |
| 定制按键 | 手动唤出画面 |

画面可显示在**主屏悬浮窗**，或推送到**副屏**（EVCC dashcast）。

【本项目】**暂时保留**，不删除。它与 `CameraRecordingService`、`MainFloatingWindowView`
有耦合，删除风险高于收益；且其显示能力（悬浮窗 / 副屏）本身在极氪上可能有用，
即使转向灯联动用不了。

### 已验证：转向灯 / 车门信号读不到，卡在权限而不是 API

2026-08-29 的实机诊断报告给出了明确结论。经过两轮猜错的探测，答案是：
**接口就在那里，能连上，只是权限拿不到。**

#### 两个被推翻的猜测

| 猜测 | 实测 |
|------|------|
| 按类名找 `CarSignalManager`（`com.gwm.*` / `com.geely.*` / `com.zeekr.*`） | 全部不存在 —— 而且这本来就不是 EVCam 的读法 |
| ECARX 那条 binder 链（`ecarxcar_service` → `ecarx.car.ECarXCar`） | **服务和类都不存在**。极氪 7X 不走 ECARX 那套 |

`com.ecarx.xui.adaptapi.car.sensor.CarSensor` 同样不存在。
EVCam 的三条路在这台车机上一条都不通。

#### 实际可用的是标准 Android Automotive

```
android.car.Car                     存在
Car.createCar(context)              成功
car.getCarManager("property")       成功
CarPropertyManager.getPropertyList()  返回 0 条
读 TURN_SIGNAL_STATE / DOOR_POS / PERF_VEHICLE_SPEED / GEAR_SELECTION
  → SecurityException: requires android.car.permission.XXX
```

也就是说：**API 正常工作，每一步都成功，最后被权限挡住。**
属性清单返回 0 条也是同一个原因 —— 没有权限的属性不会出现在清单里。

需要的权限：`CAR_EXTERIOR_LIGHTS`（转向灯）、`CONTROL_CAR_DOORS`（车门）、
`CAR_SPEED`（车速）、`CAR_POWERTRAIN`（档位/手刹/点火）。
这些在 AOSP 里是 `signature|privileged` 级别 —— 需要与平台同签名，
或者被预置到 `/system/priv-app`。**App Lab 里的第三方应用两个条件都不满足。**

已在 manifest 里声明这些权限。不是指望被授予，而是为了让结论有意义：
`checkSelfPermission` 对「没声明」和「声明了但被拒」都返回 DENIED，
不声明就分不清是哪一种。下一份报告会分别显示「已声明 / 已授予」两栏。

#### 权限保护级别（2026-08-29 实测，决定性）

之前只知道「未授予」，但那时还没声明这些权限，所以说明不了任何事。
声明之后再读 `PermissionInfo.getProtection()`，这台车机自己给出了答案：

| 权限 | 级别 | 能不能拿到 |
|------|------|-----------|
| `CAR_EXTERIOR_LIGHTS`（转向灯） | **signature\|privileged** | **拿不到** |
| `CONTROL_CAR_DOORS`（车门） | **signature\|privileged** | **拿不到** |
| `CAR_SPEED`（车速） | **dangerous** | **可运行时申请** |
| `CAR_ENERGY`（电量） | **dangerous** | **可运行时申请** |
| `CAR_POWERTRAIN`（档位/手刹/点火） | **normal** | 安装时应自动授予 |

这是个分裂的结果，比「全都拿不到」有用得多：

- **转向灯和车门确实无解** —— signature|privileged 需要与平台同签名或预置到
  `/system/priv-app`，App Lab 里的第三方应用两个条件都不满足。
- **车速、电量可以申请**，dangerous 级别会弹授权框。
- **`CAR_POWERTRAIN` 是 normal 级别** —— 这类权限本该在安装时自动授予，
  但报告显示未授予，说明容器的 PackageManager 没有代为授予。
  用诊断页的「申请车辆权限」按钮申请一次即可（normal 权限不弹框，直接通过）。
  拿到之后**档位、手刹、点火状态**就能读了。

#### 结论对补盲模块意味着什么

**转向灯联动在极氪 7X 上做不了** —— 不是找错了 API，是权限级别决定的。
补盲模块只剩手动触发可用。logcat 也扫过 6670 行、0 命中。

**但档位可以是替代触发源**：`GEAR_SELECTION` 只要 `CAR_POWERTRAIN`（normal 级别），
挂倒挡自动切后视画面是可行的方向，不需要转向灯。

### 待验证：主屏悬浮窗

**任务**：确认悬浮窗能否在极氪车机上正常显示 —— 需要「显示在其他应用上层」权限，
车机是否授予、悬浮窗是否会被系统 UI 遮挡或强制关闭、以及退到后台后是否还在。
这项即使转向灯信号读不到也有价值：可以当作常驻的小窗环视画面。

### 已确认：车机向应用暴露了三块屏

2026-08-29 的诊断报告里 `DisplayManager.getDisplays()` 返回三块：

| id | 类型 | 分辨率 | 状态 |
|----|------|--------|------|
| 0 | 内置屏幕 | 3200×2000 | ON |
| 2 | HDMI 屏幕 | 2560×536 | ON |
| 3 | HDMI 屏幕 | 1440×480 | ON |

两块副屏都是 ON，说明它们是真实在用的显示设备，不是占位。
2560×536 这个细长比例（约 4.8:1）与主屏下方的横条屏形态吻合，
1440×480（3:1）则是另一块。**具体对应车上哪块屏，需要实机推一帧上去看。**

**任务**：在这两块屏上建 `Presentation` 试推画面，确认
（a）应用是否被允许在其上创建窗口，（b）各自对应车上哪一块。
若可行，副屏常驻环视画面会是很实用的形态 —— 2560×536 正好适合放一条横向拼接的
环视带。

## 4.7 StartX BLE 旋钮（待办，尚未实现）

### EVCC 是什么

「Ecarx Vehicle Control Console」，包名 `com.kooo.evcc`，面向 FlymeAuto / 龙鹰一号平台，
进阶功能需要 Root。与 EVCam 的 `com.kooo.evcam` 同包名前缀，很可能是同一作者。

本项目已经在用它一处能力：`EvccDashcastDisplayResolver` 通过
`content://com.kooo.evcc.displays` 解析它的仪表投屏 VirtualDisplay。

### EVCC 支持 StartX 旋钮的方式

StartX 是 **BLE 低功耗蓝牙旋钮**，EVCC 把它接进了自己的自动化规则引擎：

| 项 | 内容 |
|----|------|
| 主通道 | BLE **广播包**（advertisement），不是连接 |
| 去重 | 固件写在广播负载里的「硬件序号」 |
| 旋转编码 | 右旋为正、左旋为负；一包可含 N 步，变量 `$ble_rotation_steps` 为带符号累计值 |
| 事件 | 单击 / 双击 / 长按抬起 / 旋转方向 / 累计步数 |
| GATT 连接增强 | 检测到有效操作后建约 60 秒 GATT 连接；订阅通知成功后成为唯一控制通道；最后一次旋转后约 450ms 静默窗口才发起连接 |
| 固件版本 | 1.1.4 / 1.3.0 / 1.3.1 / 1.3.2，累计字段与广播间隔策略各不相同 |

配对流程：自动化规则编辑器 →「BLE 设备信号」触发 →「StartX 旋钮」→ 配对 →
转一下旋钮让 EVCC 扫到 → 保存 MAC。

### 对本项目的三点关键结论

1. **不是标准 HID 设备。** 文档完全没提 HID —— 是自定义 BLE 协议（广播 + GATT 混合）。
   所以不能指望系统把它当键盘/媒体键把事件送进来。
2. **EVCC 没有对外接口。** 没有 SDK、没有广播 Intent、没有暴露旋钮事件的 ContentProvider；
   文档说其集成方式是 Frida 注入 + 私有 MIBO GATT 桥接。
   **无法通过 EVCC 转发旋钮事件给本应用。**
3. **广播负载的字节格式没有公开。** 文档只说日志里能看到「十六进制内容」、按硬件序号去重；
   service UUID、厂商数据结构、字节布局均未说明。

### 要实现的话，缺的是协议

技术上可行：Android 扫描 BLE 广播不需要 Root，也不依赖 EVCC。缺的只是
「广播里哪几个字节是方向 / 步数 / 序号」。获取途径按可行性排：

1. **自己抓包反推**（最现实）—— 在应用里做一个 BLE 广播嗅探页，扫描并导出原始 hex；
   慢转、快转、单击、双击各采一组，对比字节变化即可推出格式。
2. **直接问作者** —— EVCC 与 EVCam 很可能同一人，本项目已以 EVCam 为基座。
3. **厂商公开文档** —— 未搜到，但 StartX 是在售硬件，可能存在。

**不要反编译 EVCC。** 它闭源，且本项目自始至终守着「只用公开的事实信息、不碰他人代码」
这条线（见 NOTICE.md）。

来源：<https://evcc.coauto.cc/static/evcc_user_guide.md>

## 4.8 回放与解码能力（2026-08-29 实测，已排除）

一度怀疑录制尺寸超出硬件解码上限，是回放抽搐/卡死/乱码的根因。**实测排除了这个可能。**

**录出来的其实不是 1280×5140。** 开启 `grid2x2` 排列后，四路被重新拼成 2×2，
落盘是 **2560×2560 HEVC**：

```
20260829_143343_front.mp4   2560x2560  video/hevc  9fps  60秒  22.2 MB
```

**解码器绰绰有余：**

| 解码器 | 尺寸上限 | 最大并发实例 | 2560×2560 |
|--------|----------|--------------|-----------|
| `c2.qti.hevc.decoder` | 8192×4320 | **16** | 支持 |
| `OMX.qcom.video.decoder.hevc` | 8192×4320 | **16** | 支持 |
| `c2.android.hevc.decoder`（软解） | 4096×4096 | 32 | 支持 |
| `*.secure` 变体 | 4096×2304 | 3 | 不支持 |

只有 DRM 用的 `.secure` 变体吃不下，而普通文件回放根本不会走它们。

**所以：**

- 尺寸没超限 —— 回放问题就在播放器一侧（已在 0.7.4 / 0.7.6 修）
- 并发上限 16 远大于视频回看同时播的 3 路 —— **「画面变绿是解码器实例耗尽」这个猜测也不成立**

## 4.10 设置项的作用范围（2026-08-29 审计）

「帧率 / 码率 / 分辨率是全局生效，还是只对环视生效？」逐条追到落地处的结论：

| 设置 | 作用范围 | 说明 |
|------|----------|------|
| **录制帧率** | **全局**，一个值下发给所有相机 | `getActualFrameRate()` 在 `startRecording` 里算一次，循环里每一路都用同一个值 |
| **码率等级** | **全局等级**，绝对码率按每路各自算 | `getActualBitrate(w, h, fps)` 用的是**这一路自己的**分辨率，等级（低/中/高）只是倍率。这是对的：4K 的那一路和 720p 的那一路不该给同样的码率 |
| **目标分辨率** | **全局一个值**，但环视除外 | 见下 |
| 曝光 / 白平衡 / 色调 / 降噪 / 锐度 | 全局 | `ImageAdjustManager` 统一下发 |

### 目标分辨率：环视必须排除在外

环视相机不能跟着这个设置走 —— **四联合成的内容只在 1280×5140 下存在**。
选别的尺寸并不是「同一画面换个清晰度」，而是直接拿到一张普通的单画面图。

而相机 2 压根没声明 1280×800，所以按「最近匹配」会落到 1280×720：

| 全局目标分辨率 | 环视相机实际拿到 | 结果 |
|---|---|---|
| 1280×5140 | 1280×5140 | 四联画面正常 |
| 默认 1280×800 | 1280×720 | **合成内容丢失** |
| 1920×1080 | 1920×1080 | **合成内容丢失** |

单路配置一直有 `setPreferredSize(located.size)` 钉住这一路，所以不受影响；
**三路配置在 0.6.0 被我误删了这行**（当时错误地以为强制尺寸撑爆了 HAL 并发预算），
于是它只是因为用户手动把目标分辨率设成了 1280×5140 才能工作 —— 一个不该存在的依赖。

现在前台与后台两条初始化路径都钉住环视这一路，座舱两路仍按全局设置各自挑。

### 车型（视频流配置）的影响范围

选择车型会改变：

- `getCameraCount()` —— 进而决定 `requiredTextureCount`、`maxOpenCameras`、
  哪些槽位参与录制、设置页哪些勾选框可见
- 加载哪个布局（单路四宫格 / 三路 / 自定义）
- 是否走 `FourLaneContainer` 拆分、是否需要自定义布局管理器
- 预览变换分支（旋转与否）
- 切换车型时会 `resetRecordingCameraSelection()`

反过来被设置影响的只有：手动相机映射（`camera_override_*`）会覆盖自动分配的槽位。

**车型不改变**帧率、码率、画质等任何一项 —— 那些都是独立的全局设置。
