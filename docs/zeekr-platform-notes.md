# 极氪 App Lab 平台事实笔记

这份文档记录本项目开发过程中掌握的**极氪车机平台事实**：视频流格式、车机逻辑、
资源限制、以及踩过/绕过的坑。目的是让后续开发不必重新摸索。

**大部分事实来源于 [openavm-recorder](https://github.com/Dantenothing/openavm-recorder)
项目公开的 README 与源码注释**（作者 Dantenothing，保留所有权利）。这些是对车机行为的
事实性观测记录，不是代码。本项目未复制其任何源代码。**在此致谢原作者把这些观测公开出来——
没有它们，下面每一条都要拿真车去撞一遍。**

标注说明：
- 【实测】= 上游项目在真车上观测到的结果
- 【未知】= 尚未确认，不要当成事实用
- 【本项目】= 本项目据此做出的设计决定

## 1. 视频流

### 1.1 只有一路合成流，不是四个摄像头

【实测】App Lab 环境下，第三方应用通过标准 Android Camera2 拿到的是
**一路已经处理好的合成流**，不是四路独立摄像头，也无法请求四个独立的相机设备。

### 1.2 尺寸与排布

| 排布 | 尺寸 | 构成 |
|------|------|------|
| 竖排（实测车机给的就是这个） | `1280×5140` | 四个 1280×1280 方形画面竖向堆叠 + 5 条 4px 分隔带 |
| 横排 | `5120×1280` | 四个 1280×1280 横向排列，`5120 = 4×1280`，无分隔带 |

竖排的算法：`5140 − 4×1280 = 20`，均分给 5 条分隔带（上边缘、三条内部分隔、下边缘），
每条 4px。分隔带在画面上表现为细线。

【本项目】`CompositeStreamGeometry` 按此实现，并在排布对不上时安全回退为四等分。

### 1.3 HAL 可能给一个压扁的小尺寸提示

【实测】车机 HAL 有时只声明一个较小的 Surface 提示尺寸（例如 `640×480` 附近），
但内部送来的**仍是同一份四联合成内容**，只是被压扁了。

上游的做法是：预览优先选择最接近 `640×480` 的普通声明尺寸作为稳定回退，
只有当 SurfaceTexture 明确声明了 `1280×5140` 时才请求那个大缓冲区。

【本项目】拆分几何一律按**合成流真实尺寸**计算，得到归一化窗口后再套到实际绘制区域。
这样缓冲区无论多大、是否被压扁，四个画面的位置与比例都正确。
`FourLaneContainer.setSourceSize()` 会忽略"不像合成流"的尺寸，避免把已探测到的正确几何降级。

### 1.4 绝不要臆造分辨率

【实测】上游明确的工程原则：只使用 HAL **实际声明**的尺寸，不做近似替换、不做隐式回退。
拿一个没被声明的尺寸去开相机，结果是黑屏或直接失败。

【本项目】`ZeekrCompositeProfile` 遵循同样的原则，一个候选都没有时返回"未找到"，
由界面明确提示用户，而不是硬开。

### 1.5 编码参数

【实测】整条合成流的实际录制表现：

- 编码码率约 **28 Mbps** @ `1280×5140`
- 落盘速度约 **200 MB/min**，即 **3–4 MB/s** 持续写入
- 一小时录制约产生 **12 GB** 主机层写入量（还没算文件系统与闪存写放大）

## 2. 渲染：一个必须避开的坑

### 2.1 用 GL 自建 SurfaceTexture 顶替生产者会崩溃

【实测】**这是本项目最重要的一条平台事实。**

直觉上最优雅的做法是：在 GL 线程建一个外部纹理（OES），把它的 SurfaceTexture 交给
Camera2，然后用着色器把四个画面渲染成四宫格。**这条路在真车上崩了。**

上游源码注释原文：

> "The old automatic preview crashed because it replaced the working producer with a
> GL-owned SurfaceTexture. The current path has been verified on the car: Camera2 feeds
> one ordinary TextureView and its parent redraws that same child into four cells."

### 2.2 验证可行的结构

```
Camera2 ──写入──> 一个普通的 TextureView（唯一的相机消费者，不被改造）
                        │
                        │ 父容器把同一个子视图重复画 4 次，
                        │ 每次裁剪到一个格子并映射对应的源矩形
                        ▼
                   2x2 四宫格
```

关键在于**相机链路一点都不动**，只改变"这个已经在正常工作的子视图怎么被画出来"。

【本项目】`FourLaneContainer` 采用这套结构。本项目最初写的是 GL 方案，
读到上游这条注释后**整体推翻重写**——这正是读代码学事实的价值。

## 3. 车机逻辑

### 3.1 相机所有权：原厂功能优先

【实测】原厂车辆软件可能随时接管相机资源，用于：

- 原厂 360° 环视
- 倒车影像
- 泊车辅助相机功能
- 其他 OEM 相机接口

应用**必须让路**。当 Android 报告相机不可用或已被占用时，正确做法是：

1. 停止或暂停录制；
2. 让原厂功能保有相机；
3. 只在原厂功能释放之后再重试。

**第三方应用永远不能被视为优先于原厂车辆功能。**

【本项目】EVCam 基座自带 `CameraRecoveryStateMachine` 式的重建与退避逻辑；
后续应针对极氪补一条"确认被原厂接管时不要抢"的策略。**这是当前待办项。**

### 3.2 App Lab 存在资源管理策略

【实测】App Lab 界面自身的提示：

- **体积过大的应用可能无法启动**；
- App Lab 应用在车机其他功能高负载时**可能被降速**。

【未知】具体的 CPU/GPU/RAM/存储 I/O 限制、调度优先级、是动态还是固定、
哪些原厂负载优先——全部未公开、未验证。

【本项目】APK 体积是一个真实风险：本项目继承了 EVCam 的全部依赖
（钉钉 SDK、gRPC、Glide、OkHttp、NanoHTTPD 等），**CI 实测 release APK 约 24 MB**，
比上游那个精简 Compose 应用大不少。若遇到装不上或起不来，缓解顺序：
① 开启 R8（`isMinifyEnabled = true`）+ 资源裁剪——注意 Gson/gRPC/钉钉 SDK 用反射，
必须配 keep 规则并实机回归；② 砍掉用不到的远程查看模块。

### 3.3 内存

【实测】录制过程中车机系统报告约 **9 GB 可用 RAM**。
这只是系统自报值，说明该工况下没有明显内存压力，
但不构成对内存带宽、分配延迟等共享资源的度量。

### 3.4 实测路试

【实测】截至 2026-08-12，上游累计约 **4 小时实车路试**，
条件为：后台持续录制 + Android Auto 同时正常运行 + 正常用车。

期间未观察到：录制失败、明显卡顿/丢录、Android Auto 异常、
原厂 360° 相机异常、车辆异常、车机故障。

这是有用的经验证据，但**不构成长期安全性、零资源开销或普适兼容性的证明**。

### 3.5 一次与本应用无关的车机中断

【实测】在**任何第三方 App Lab 应用安装之前**，测试车曾出现过一次完整的车机中断：
中控黑屏、HUD 同时不可用、持续约两分钟后自行恢复，期间基本驾驶功能未受影响。

这条只作为测试背景记录，既不能说明原因，也**不能证明第三方应用永远不会引发类似问题**。

## 4. 存储

### 4.1 App Lab 不允许直接写外置 U 盘

【实测】**这条对本项目影响很大。**上游原文：

> "The tested App Lab environment does not currently allow AVM Recorder to write
> recordings directly to external USB storage."

录制因此只能落到应用内部存储。

【本项目】EVCam 基座带有完整的 U 盘存储支持（检测、公共目录写入、中转写入、掉盘回退），
这也是当初选它做基座的理由之一。但在极氪车机上**这套功能很可能直接不可用**。
代码保留（换台车/换个固件也许能用），但 README 已明确标注该限制。
**这是需要实车确认的第一批事项之一。**

### 4.2 闪存写入量

【实测】自动清理只控制"占用空间"，不减少"累计写入量"。
删旧片段再写新片段，占用可以基本恒定，但底层 NAND/UFS/eMMC 的写入是持续累加的。

按 200 MB/min 算，一小时约 12 GB 主机层写入。

【未知】车机内部存储的器件型号、NAND 类型、耐久度评级、预留空间、
磨损均衡策略、文件系统写放大、寿命写入计数器——全部未知。

**内部闪存耐久性因此是一个未解决的风险。**

【本项目】上游给出的工程建议值得照做：
**避免不必要的临时文件与中间落盘，尽量在内存中处理，只持久化最终编码结果。**
注意 EVCam 的"中转写入"（先写内部再异步搬到 U 盘）正好与此相悖，
在极氪上既没必要（U 盘写不了）又会翻倍写入量——**应默认关闭**。

## 5. 权限与网络

【实测】上游应用只申请：相机、通知、前台服务、唤醒锁。
**明确不申请 `INTERNET` 权限。**

【本项目】EVCam 基座包含钉钉/飞书/Telegram 远程查看、MJPEG 推流、心跳推图等功能，
因此**申请了网络权限**，攻击面明显更大。用户若不需要远程功能，
建议在设置中全部关闭。后续可考虑做一个无网络的精简构建变体。

---

## 6. 构建环境

【实测】上游的构建要求：Android SDK API 36、JDK 17、Gradle wrapper。
本项目一致（compileSdk 36 / minSdk 28 / JDK 17）。

安装方式：下载签名 APK，通过系统/App Lab 的安装流程安装，启动后授予相机权限。
