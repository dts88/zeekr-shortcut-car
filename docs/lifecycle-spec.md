# App 生命周期规格

这份文档是**定义的唯一出处**：照现在的代码写规矩、谁来判、谁照做，每条注明在哪一处判（类名.方法）。
规矩由项目所有者定，改规矩先改这里；项目所有者定的写上日期。以前怎样、哪一版改的不在这里，看 git 和 CHANGELOG。
还没做到、还没定的记在第 8 节。

平台上的实测事实（车机会不会睡、哪些广播收得到）在 `zeekr-platform-notes.md` §3.6，这里只引用结论。

---

## 0. 总原则（2026-09-26）

**用户设定了一个状态 —— 也就是用户认为这个 App 正以什么状态运行 —— App 就应该保持在那个状态运行。**
只有停车、软件异常、存储满这类特殊情况下，才根据我们的设置和规则临时调整；特殊情况一结束，回到用户设定的状态。

下面每一条规矩都是这条原则在某个具体场景里的展开。规矩没覆盖到的情况，按这一条判断。

**「用户设定的状态」就这几样**：录像开不开、悬浮按钮开不开、超级镜子开不开，各在自己的分区里；盲区画面开不开
（2026-10-17），是超级镜子分区里单独的一组。「启动自动录制」也是设定状态的一部分（§3.2）。

**两个规则开关**不定义状态，只回答两个问题（2026-09-27）：

1. **App 自己不在了（被杀、重启后没起来），要不要自己回来？** —— 「开机自启动」（「系统」分区，§2.5）。
   App 还在的时候回到设定状态不需要开关，那是本原则本身；保活（§6）负责让 App 尽量别不在，也归这个开关管（2026-10-08 并入）。
2. **熄屏算不算「出状况」，要不要停录？** —— 「熄屏持续录制」（「录制」分区「自动录制」一组，和「启动自动录制」放在一起，
   2026-10-19）。熄屏是屏幕真黑了；黑满 30 秒时哨兵模式开着才接着录环视，座舱放开（2026-10-12、10-27，§3.3）。

「诊断信息」不在这套逻辑里：它只要把车机干了什么记清楚，方便开发上面这几项（§7）。

## 1. 框架：一处判断（项目所有者 2026-11-02）

控制相机和录像的判断只在一处 —— 相机管家；别处只请求、或者照做（项目所有者 2026-11-02：「用于控制摄像头行为的模块太多了，
应该收于一处」；录像协调器同日抹掉，必需的功能照实际需要交给相机管家）。

| 层 | 是谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 请求方（§2） | 主界面、悬浮按钮和灵动贴、超级镜子、盲区画面、开机自启动和保活、设置 | 说要什么：要不要相机、开始 / 停止录像、拍一张、退出；报自己看到的事实：屏幕亮了、应用被带回来、主界面打开了 | 不开关相机、不改会话、不判录不录、停不停 |
| 相机管家（§3、§4） | `CameraKeeper`（对外唯一入口）；规矩 `ChannelRules`；登记表 `CameraNeeds`；通道调度 `ChannelScheduler`；让了再试的账 `CanvasSlot`、`RecordRetries` | 判：谁要哪几路、开哪台关哪台、录不录、停不停、熄屏怎么办、会话装不下谁先让、让了什么时候再试、前台服务开不开、退出的次序 | — |
| 执行方（§5） | 相机层 `SingleCamera`（一台相机）、录像宿主 `MultiCameraManager`（每一路的录制器）、画布（三方的 TextureView 画布） | 照调度下达的一步做；把发生了什么报上来：出画面了、丢了一个输出、写不进、被断开 | 不自己决定开关、不自己重试 |

- **规矩是纯函数**（`ChannelRules`）：输入是此刻的事实（登记表、屏幕、车辆信号、每一路的样子），输出是该怎样；
  数字照批过的写死在单元测试里。改需求只改规矩那一条，不碰别的逻辑。
- **动相机只有调度**：进程里只有一个调度（`ChannelScheduler.app()`），一次一步（§4）。开、关、改输出、救援都是它下达的一步，
  相机层照做。
- **对外一份状态**，都问相机管家，谁也不自己记：在不在录（`CameraKeeper.isRecording`）、录像此刻的样子（`view`：空闲 / 开录中 /
  在录 / 等待摄像头）、每一路的样子（`summary`）、录制键小字（§3.3）、前台通知的字（`notificationTitle`、`notificationContent`）。
  主界面、悬浮按钮、前台通知、自动锁定都照它。
- **事实也只有一份**：屏幕黑没黑只问 `ScreenState`（§3.3）；相机服务说的话只经 `CameraAvailabilityWatch`；叫醒调度的进程层监听
  （亮熄屏、登记表、相机服务、车辆信号）在 `ChannelFacts`，挂一次；别的事实（前台服务起来了、没了，车机要睡，车机醒着屏幕黑着，
  设置变了）经相机管家叫醒调度（`CameraKeeper.factsChanged`）。管线也向相机管家要（`pipeline`、`commitConfigForMainScreen`、
  `checkPipeline`），谁都不直接去建、去换。

**代码地图**（在 `camera` 包里，另注的除外）：

| 类 | 是什么 |
|---|---|
| `CameraKeeper` | 相机管家的入口：请求、事实、状态；录像的开、停、接回，「这一趟」 |
| `ChannelRules` | 全部规矩（纯函数） |
| `CameraNeeds` | 登记表：谁要相机、要哪几路（§3.1） |
| `ChannelScheduler`、`ChannelFacts` | 通道调度，唯一动相机的地方；叫醒它的进程层监听（§4） |
| `CameraManagerHolder` | 相机管线：建、放、重建（§4.9） |
| `MultiCameraManager` | 一份管线：各路相机；录像宿主（录制器、每一路进出） |
| `SingleCamera` | 相机层：一台相机的打开、会话、输出（§5.1） |
| `CanvasSlot`、`RecordRetries` | 让了之后什么时候再试的账：画布、录像（§3.4） |
| `RecordingLanes` | 录像每一路的表（§3.2） |
| `screen.ScreenState` | 屏幕黑没黑，唯一一份（§3.3） |
| `recovery.Recovery` | 进程回来、车机醒来时照设置把东西带回来（§2.5） |
| `StallWatch`、`blackbox.BlackBox`、诊断报告 | 只读、只写记录（§7） |

## 2. 请求方

每一方只说要什么、报自己看到的事实；判断和动相机都在相机管家（§1）。

### 2.1 主界面（`MainActivity`）

- **预览**：启用的那几路各一格（§3.1），每格一块画布交给相机管家（`CameraKeeper.canvas`，§5.3）。接上了管线、各格画布都就绪才登记
  要相机（`need(PREVIEW)`），`onPause` 注销；界面因为配置变化重建时不注销，留给新界面。熄屏时预览不算（§3.1）。
- **录像**：录制键 `startByUser` / `stopByUser`（`Why.USER`），录到内置存储之前先问一句。界面只照相机管家的状态画（`view`、`summary`、
  计时），不自己记在不在录。
- **拍照**：`takePhoto`（§3.5）。
- **退出**：`beginExit`，次序由相机管家定，主界面只做界面那几件（§3.5）。
- **报的事实**：人自己点开主界面是新的一趟（`newTrip`，§2.5）；界面打开、回到前台（`mainScreenOpened`、`mainScreenShown`：相机管家看
  「这一趟要录」、看一次「启动自动录制」，§3.2）；界面没了（`mainScreenGone`）。
- **管线**：向相机管家要（`CameraKeeper.pipeline`）；摆好录制界面时请它让存下的配置生效（`commitConfigForMainScreen`，§2.6）。
  管线换了，主界面自己把界面的回调接到新的一份上（`pipelineReplaced`）；预览画布由相机管家重新交（§5.3）。
- 相机管线不属于主界面（§4.9），录像不经过它。它只在一种时候非出来不可：后台起的前台服务用不了相机（安卓 12），这时要录，
  相机管家把主界面拉起来一次（§2.5）。

### 2.2 悬浮按钮、灵动贴（`QuickActions`）

两边按下去走同一份（`QuickActions.perform`），黑匣子照 `Why.FLOATING` / `Why.BUTTON` 记是谁按的。

- **录制**：主界面在前，交给主界面（和点录制键一样，录到内置存储之前它先问）；不在前，直接 `toggleByUser`，用不了相机时
  相机管家把主界面拉起来。
- **拍照**：`takePhoto`，和拍照键同一个入口。
- 别的动作不碰相机。

### 2.3 超级镜子（`RearViewMirrorService`）

- **要相机**：窗口在显示、没贴边、屏幕没黑时登记 `need(MIRROR)`；贴边、熄屏、摘下时注销。只放登记，画布留在会话里，
  放回来、亮屏时画面马上就有（§4.4）。
- **画布**：环视一块；切换范围是「后视 + 后座舱」时后座舱再一块，看后视时后座舱那块也交着，切过去不用等。两块都交给相机管家
  （§5.3）。两块总有一块看不见，看不见的 TextureView 不自己建画布，由服务建。
- **让了再试**：相机层这一回不带它（录像中会话配不上，§3.4）时，重新打开窗口、亮屏、放回来、点「点击恢复」时再试；
  管线换了相机管家自己再试。看门狗每 2 秒再交、再登记一次，但不试让掉的。
- **管线换了**：相机管家把交着的画布声明到新的一份上，再叫它对一次（`onRebuilt` → `ensureStillBound`：看得见、没贴边、亮着屏才登记），
  新管线第一轮就带着它（§5.3）。
- 「后视 + 后座舱」而管线里还没有后座舱：打开超级镜子、切到这一档时请相机管家对一次管线（`CameraKeeper.checkPipeline`），
  当场放掉重建（§4.9）。

### 2.4 盲区画面（`SideViewService`）

- **画布**：中控屏两块（`SIDE`、`SIDE_SECOND`）、HUD 一块，都在环视上，和预览、超级镜子挂在同一条共享预览流上（§5.1）。
- **要相机**：功能开着、亮屏，窗口挂上时（挂 D 挡时隐藏着备好，或者正在显示）交画布、登记 `need(SIDE_VIEW)`；离开 D 挡 30 秒、
  熄屏、原厂画面出现（倒挡、原厂 360、原厂侧方小窗、泊车辅助）、关掉功能时窗口移走（`SideViewTrigger`），三块都移走了才注销。
  窗口移走时画布交给管线留着，下一次挂窗口接回同一块（§5.3）。
- **让了再试**：相机层这一回不带它（共享预览流挂不下、会话配不上时它最先让，§3.4），或者窗口挂不上：这一段不再挂，
  等这一段结束（离开 D 挡 30 秒、熄屏、原厂画面之后）再试。管线换了不试。
- **管线换了**：相机管家声明完画布，各块窗口挂着、亮着屏的再对一次、登记（`onRebuilt`）。

### 2.5 开机自启动、保活、恢复（`Recovery`）

**定义（2026-09-26）**：在车机启动后、从休眠中恢复后、从任何不正常状态恢复到待机模式后，让 App 恢复到正常开机时的状态 ——
用户开着超级镜子、盲区画面、悬浮按钮、自动录制的，都恢复。车辆是不是真的在休眠、黑屏是不是哨兵模式、车辆是否把 App 杀了，
不在开机自启动的考虑范围。原则层面（2026-09-27）：收到各类信号，判断自己能正常运行了，就接手，把用户设定状态里开着的那几样
（录像、悬浮按钮、超级镜子、盲区画面）起来。「保持后台运行」并进这个开关（2026-10-08），默认开。

- **什么算恢复**：App 能确定自己是从不正常状态恢复到正常的，就算醒来，按开机自启动处理；自己感知不到的（被冻结了、
  自己都不知道进入过黑屏 / 休眠 / 冻结）视为没有变化。
- **恢复到哪里：恢复被打断的，不推翻用户做过的决定**。「这一次开机里用户做的选择」（手动停录、点了退出）记在「这一趟」里
  （`CameraKeeper` 的 `Trip`，落盘）：

  | 事件 | 这一趟 |
  |---|---|
  | 车机真正开机（`BlackBox.rebootedSinceLastRun`） | 新的一趟（`newTrip`），回到设置的状态 |
  | 人自己点开主界面 | 新的一趟 |
  | 深睡醒来 | 还是这一趟，恢复到睡前 |
  | 进程被杀、又被我们拉回来 | 还是这一趟，恢复到被杀前 |

- **车机停车后自己醒的那一次，同样恢复**：停车约 2 小时 5 分钟后车机会自己醒来、亮屏约两分钟。醒来时进程还活着，按 §0 回到设定状态
  （`Recovery.restore`：悬浮按钮、超级镜子、盲区画面照设置起），不拉主界面。车没通电（点火 ACC 或更低）时屏幕亮了不算亮屏，
  还是熄屏（§3.3「车机醒着、屏幕黑着」）：相机一路都不开，录像不开录；之后熄屏中哨兵模式变成开才开环视录（§3.3）。点火读不到的，
  醒来那一遍只看安卓，算亮屏。
- **用户退出后暂停自启动**，直到下一次车机真正开机，或者人自己打开（`UserExit`）。
- **恢复可能有延迟**：只有我们的代码有机会运行时才能恢复 —— 醒来后一秒内（保活任务必跑），进程被杀后最慢 15 分钟（保活任务的周期，§6）。
- **恢复自动录制时主界面会闪一下**（约半秒到一秒，再自己退到后台）：后台起的前台服务用不了相机（安卓 12），要录时相机管家
  让主界面在前一次，相机才开得起来（`Recovery.bringUpMainForRecording`）。只在两下判：打开录像意图那一下、亮屏那一下
  （`CameraKeeper.bringUpMainIfCamerasUnusable`）；屏幕黑着时不拉。已经在录时才变成用不了的（录着时前台服务在后台被系统重启）不拉，
  录像「等待摄像头」到主界面回到前台、或者下一次亮屏 —— 很少见。
- 恢复是请求方：它照设置把服务带回来、告诉相机管家应用回来了（`appRestored`），录不录、开不开相机由相机管家判（§3.2）。
  保活的几种拉起（广播、ContentProvider、无障碍服务）都只请相机管家把前台服务对一次（`ensureForegroundService`，§3.5）。

### 2.6 设置

- 改了设置回到主界面时生效，不用重启：要建的几路、各路参数、摄像头映射变了，管线在主界面下一次接上时照此刻的设置重建
  （主界面请相机管家，`CameraKeeper.commitConfigForMainScreen`，§4.9）。超级镜子切到「后视 + 后座舱」而管线里没有后座舱，
  设置页请相机管家对一次管线（`checkPipeline`），当场重建；调度现读的那几样变了，请它叫醒调度（`factsChanged`）。
- 「开机自启动」变了：请相机管家把前台服务对一次（`refreshForegroundService`，§3.5）。

## 3. 相机管家

相机管家（`CameraKeeper`）是唯一判断的地方：登记表记谁要（§3.1），规矩在 `ChannelRules`，通道调度照它动相机（§4）。
这一节是判什么、怎么判；怎么动相机在 §4。

### 3.1 登记表（`CameraNeeds`）

一张「谁要哪几路」的登记表（项目所有者 2026-10-10 定「登记表 + 一个调度」）。要用相机的各自登记、用完注销；**登记表只是数据，
自己不动手**，变了就叫醒调度。「谁在用，都不用了才释放」照旧成立，只是「都不用了」按每一路算（下面「保持」）。

| 谁 | 要哪几路 | 要什么输出 | 什么时候算 |
|---|---|---|---|
| 主界面预览（PREVIEW） | 启用的全部（主界面只给它们摆格子） | 预览 | 各格画布都就绪、主界面接上了管线时登记，`onPause` 注销（重建时不注销）；熄屏时不算：主界面看不见 |
| 录像（RECORDING） | 这次录像计划里的；被存储一类打断、等自动接回时是启用的全部 | 录像 | 录像意图开着（查过盘之后，§3.2）；存储一类停了、等自动接回时留着；在等 U 盘的不登记 |
| 拍照（PHOTO） | 启用的全部 | 会话里常驻的 JPEG（不改会话；相机没开时先按次序开，带不显示的出帧口） | 按下拍照（主界面、悬浮按钮、灵动贴）、查过有地方存之后，到这一张存完或放弃 |
| 超级镜子（MIRROR） | 环视（配置里没开环视也要，2026-10-16）；切换范围是「后视 + 后座舱」时还有后座舱（配置里没开也要，2026-10-19） | 超级镜子（后座舱那一档两路各一块画布） | 窗口在显示、没贴边、屏幕没黑时登记；贴边、熄屏、摘下时注销（§2.3） |
| 盲区画面（SIDE_VIEW） | 环视（配置里没开环视也要，2026-10-16） | 盲区画面（和预览、超级镜子挂在同一条共享预览流上） | 窗口挂上、亮着屏时登记；三块窗口都移走了注销（§2.4）；相机层丢了它、窗口挂不上时这一段不再登记 |
| 保持 30 秒 | 刚才开着、现在没人要的那一路 | 留着的活输出；一样都没有才补出帧口 | 每一路没人要之后各自算（下面「保持」） |

- **启用的** = 配置里开着的那几路（`RecordSpecs.enabledCameraKeys`，建管线那一刻的；调度里是 `ChannelRules.World#enabled`）。
  主界面的布局、要等的画布也只问这一个函数，不数路数。建管线时环视一直建（超级镜子、盲区画面要它），座舱启用了才建；建了不等于开。
  后座舱另外在超级镜子的切换范围是「后视 + 后座舱」时也建，但不算启用的：主界面不给它摆格子，预览、拍照、录像都不要它
  （什么时候为它重建，§4.9）。这一档的代价（2026-10-20 记下）：超级镜子贴边、熄屏、摘下后，后座舱没别人要就保持 30 秒后关，
  照「关座舱前先关环视」环视（含环视录像）断约 0.5–1 秒、录像多切一个文件（贴边照现行调度逻辑，项目所有者 2026-10-16 定）；
  后座舱照开的次序排在前座舱前面，它一帧不出时前座舱的开、录像加入要等它那一步（最多 15 秒）。
- **一路该开** = 不在退出、车机不睡，并且有人要、或者在保持（`ChannelRules.shouldOpen`）。
- **什么时候算谁**（项目所有者 2026-10-27）：登记表照记，算不算看此刻是哪一段（`ChannelRules.holderWants`、`wantsKind`）。
  「通道算黑」= 屏幕黑满 30 秒、或者黑着时安卓熄屏（`ChannelRules.darkForChannel`，§3.3）；「在开车」照 `ChannelRules.driving`（§3.3）。

  | 此刻 | 环视 | 座舱 |
  |---|---|---|
  | 亮着；黑了还不到 30 秒 | 照上表，谁登记着都算 | 照上表；黑了不到 30 秒时关着的不开 |
  | 通道算黑，在开车 | 照上表（不按熄屏放开） | 放开，谁都不算 |
  | 通道算黑，没在开车 | 只算录像，而且环视要留着（§3.3「环视留不留」）；预览、超级镜子、盲区画面、拍照都不算，会话里只要录像输出 | 放开，谁都不算 |

  黑着时登记着的超级镜子、拍照照样记在表上，只是不算；亮屏又算。表不加登记方、不加标记，这一条只在通道的规则里。
- **保持**只在开着、亮屏（黑了不到 30 秒也算）、前台服务在、没人要还不到 30 秒时（`ChannelRules.holding`）；每一路各自算
  （项目所有者 2026-10-11）。通道算黑、没有前台服务（后台拿着相机安卓要求有它）、车机要睡、退出时都不保持，没人要的当场按次序关。
  关着的路不会为了保持去开。30 秒是项目所有者 2026-10-09 定的：最小化、进诊断信息 / 回看，报告里 79% 在 30 秒内回来。
  只开超级镜子、主界面最小化时，两路座舱各自保持 30 秒，30 秒内回到主界面通道零变动。
- **退出**：登记表全部作废（§3.5）。
- 主界面退到后台、熄屏、超级镜子摘下、停录、拍完，做的只是注销登记（或者什么都不做：熄屏时预览本来就不算），不各自关相机。
  登记表变了只叫醒进程里那一个调度：应用一起来、装上调度时接一次，不摘。

### 3.2 录像

**定义（2026-09-26、09-27）**：软件启动后，只要没有遇到问题 —— 存储是外置存储器、剩余空间符合要求 —— 就自动开始录制，
效果与用户每次打开主界面后直接点录制一致（「启动自动录制」）。用户手动结束录制，不影响下一趟继续自动录制（§2.5「这一趟」）。
原则：**软件在跑，就一直录，行车停车都一样；软件被杀、车机睡了，录不了就录不了，不勉强，把记录留下。**
正常状态下不会自己停：存储上限设好了，满了从最老的录像开始清理。

**一个入口**：录制键、悬浮按钮、灵动贴、启动自动录制、亮屏接着录、被打断后的接回、进程被车机结束后的接回，都经相机管家走同一条路 ——
`startByUser` / `stopByUser` / `toggleByUser` 是人按的，其余是它自己看着事实判。只有它一个等开录的轮询（查盘、等 U 盘、等上一次收拾完、
等管线建好）、一份接回额度。谁要的记在 `Why`：`USER`、`FLOATING`、`BUTTON`（人按的）、`AUTO_START`、`RESUME`、`SCREEN_ON`、`SENTRY`。

- **什么时候看「启动自动录制」**（`ChannelRules.autoStartMoment`）：应用启动（主界面打开、开机自启动把应用带回来）、屏幕亮着、
  这一趟还没看过。看过（开关开着就开、关着就不开）、人开过或者停过就不再看；开关是这一趟中途打开的，下一趟才自动开。
  屏幕黑着不看，等亮屏（项目所有者 2026-10-27：不为中间不明原因的启动去试着录）。亮屏本身不是启动，只接「这一趟要录」。
- **「这一趟要录」**（`Trip.wanted`，落盘）：开了录就立着，人停了就撤；被打断等接回、因熄屏停下等亮屏接时留着。亮屏、应用被带回来、
  主界面回到前台时，它立着、又没在录没在等，就接着录（`Why.SCREEN_ON`）；进程被车机结束后又起来也照它。新的一趟撤掉（§2.5）。

**开录**（项目所有者 2026-10-10，取代「能获得视频流以环视为准」）：查过盘、写得下，就打开录像意图，定下这次录哪几路、写到哪；
不等环视，也不等相机开完。每一路的相机带着录像输出出了画面，那一路就加入 —— 第一次开录和中途接回是同一件事（下面「每一路各自进出」）。
拿不到画面时录像意图照样开着、显示「等待摄像头」，画面一来就录。

- **能不能录**：至少选了一路、有 U 盘、写得下。U 盘不能用就等，一能用就开（项目所有者 2026-10-13）：从第一次被拒起头 2 分钟
  每 2 秒查一次（这台车机收不到 U 盘插拔的广播，盘回来没有人叫），之后、以及别的原因（盘满、一路都没选）每 30 秒一次
  （`ChannelRules.nextStartCheckMs`）。盘满了设了容量上限就删最旧的，没设就提示。
- **相机关着的那几路**，调度开之前最多等它的录像输出 2 秒（录制器在建），备好了就带着它开，省一次改输出；到点还没好先开，之后再一步
  「改输出：加 录像」。**开着的那几路**，调度一路一路加上录像输出，环视在先，每一步等安静、等上一步做完（§4）。
- 后台开录而现在用不了相机（安卓 12）、屏幕亮着：把主界面拉起来一次（§2.5）。屏幕黑着时来的「要录」照 §3.3「黑着时开录」。

**一次录像的阶段**（`ChannelRules.RecordPhase`）。「在不在录」只有这一个答案（`CameraKeeper.isRecording`；2026-10-05 批准）：

| 阶段 | 从什么时候起 | 算不算「在录」 |
|---|---|---|
| 空闲 | 上一次收拾完了 | 不算 |
| 开录中 | 录像意图开了（查过盘、写得下之后） | 算 —— 通知、悬浮按钮、录制键都从这一刻起 |
| 在录 | 至少一路加入过 | 算 —— 之后一路都不在录（等待摄像头）也还是它；一路退出、加入不改这一段 |
| 停录中 | 停了（任何原因），相机层还在收拾 | 不算；这期间不开下一次，要录的先等着，收拾完立刻开 |

**录像此刻的样子**是另一件事（`CameraKeeper.view`，照各路的摘要定，`RecordingLanes.summarize`）：有一路在录（写进过第一笔）是「在录」；
一路都没在录、而有一路在起来（在开的次序里排着、在开、或者已经出画面、录制器在备），这个录像意图里还没离开过「准备中」就是「准备中」，
离开过就是「等待摄像头」；一路都没在录、也没有一路在起来（都被拿着、在救、停手、现在用不了相机，或者录制器建不起来）是「等待摄像头」。
离开了「准备中」就不再回去。录制键、前台通知、悬浮按钮、黑匣子都照它（ui-spec 八）。计时从第一笔数据开始算；等待摄像头之后
第一路接回，「本段」的进度从接回那一刻重新算。

**停只有一条路**（`CameraKeeper.end`）：人停的、熄屏停的、盘满、写不进、一笔没写进、录制器都建不起来、录着的那份管线被释放或换掉，
都走这一处 —— 收通知、悬浮按钮，提示，判接不接；相机层按同一套收拾（各路收尾封好文件、录制器停放、作废排着的任务），
不管开录走到了哪一步。停录不动相机：录制器停放，录像输出留在会话里（§4.4、§5.2）。收拾完了报上来才回到空闲；20 秒
（`ChannelRules.STOP_DEADLINE_MS`）还没报完就不等了。相机层报上来的开录、停录（`PipelineReport`）只在对得上的阶段算数，
过时的、重复的不理（`ChannelRules.onPipelineReport`）。

| 停录原因（`ChannelRules.RecordStop`） | 提示用户 | 自动接回（`ChannelRules.resumesAfter`） |
|---|---|---|
| 人停的（`USER`：停止键、退出） | 「录制已停止」 | 永远不接 |
| 一笔都没写进（`NO_DATA`：一路在录了 15 秒一个字节都没写进，而它的相机在出画面、会话里带着它的录像输出） | 「录制未能启动，正在自动重试…」；额度用完是「录制仍未能启动，请点击「开始录制」」 | 接 |
| 开录失败（`START_FAILED`：还没有一路加入时，计划里每一路的录制器都建不起来；或者相机层没能开始 —— 查完盘之后盘没了、没有能录的一路） | 同上 | 接 —— 用户要录，只是这一次没起来 |
| 录着录着写不进（`WRITE_STALLED`：相机好好的，盘或编码器的事） | 「录制中断：无法写入文件，正在自动恢复…」；额度用完是「录制中断：无法写入文件」 | 接 —— 重开一次就是新编码器、新文件 |
| 原因未知（`UNKNOWN`：录着的那份管线被释放、换掉；或者有一路加入过之后每一路的录制器才都建不起来） | 「录制中断：原因未知，正在自动恢复…」；额度用完是「录制中断：原因未知」 | 接，管线换了的在新的那一份上 |
| U 盘满了没设上限（`STORAGE_FULL`）、清不出空间（`STORAGE_CANNOT_FREE`）、锁定的占满了（`STORAGE_LOCKED`） | 存储那边原有的提示 | 不接 —— 接回去也录不下 |
| 因熄屏停的（`SCREEN_OFF`，§3.3） | 「熄屏后已停止录制」 | 不在这里接：亮屏接不接，停的那一刻照 `resumesOnLit` 定好（§3.3） |

**摄像头被拿走、断开、卡住都不是打断**（项目所有者 2026-10-10）：那一路自己收尾退出、回来自己加入，别的路照录；一路都录不了时
录像也不算停，显示「等待摄像头，恢复后自动继续」，没有接回次数。

**写不进的裁判只有录制器一个**（项目所有者 2026-09-27）：从开录或最后一次写进文件起 15 秒没有新数据（开机时长，深睡不算）就报一次 ——
这 15 秒里它自己换盘、重建编码器、快速恢复（§5.2）。报上来的分两种（`RecordingLanes.stallIsCamera`）：这一路的相机没在出画面、
会话里没有它的录像输出、或者 2 秒内没出过画面 —— 相机的事，只这一路退出；三样都好好的 —— 盘或编码器的事，整次停：这一次录像
写出过数据的算 `WRITE_STALLED`，一笔都没写出过的算 `NO_DATA`。看的是这一次录像，不是那一路这一次加入。

**自动接回**（项目所有者 2026-10-11）：这是 §2.5「恢复被打断的，不推翻用户做过的决定」在录像上的做法。

- 打断要记进日志，并告诉用户被什么原因打断；在自动恢复的话也提示。收拾完、查过盘就重开（`Why.RESUME`），不等环视、也不等主界面。
- **判了自动接回，「录像要用相机」留着**：相机不放、停放的录制器留在会话里，接回开录时直接加入；接回被拒（等 U 盘）、不接了就放。
  写不进（`WRITE_STALLED`、`NO_DATA`）报上来的那一路例外：它的录制器停放好就换下来，接回时另建一个 —— 毛病可能就在那个录制器自己，
  沿用的话每次接回都重演。
- 手动开的录像被打断，同样接回（按 §0）。不接的只有人停过的、这一趟从没开过录的（开录前就被拒了，比如没插 U 盘）；
  开录指令发出去就算开过录。
- **额度**：连着 3 次（`ChannelRules.RESUME_TRIES`）都没有一路录满一分钟（`RESUME_COUNTS_MS`；一路都不在录、开录中的那几段不算）
  就不再试，并提示用户。成功的标准是录满一分钟，不是开始录了 —— 开始就清零的话，一直写不进时会无限循环。录满了额度回满，人开始录时清零。
- **熄屏时照样接回**：存储一类打断后的接回接的是通道允许、正在录的那一次，不看黑着开不开，安卓熄屏着也接；
  通道判了熄屏停的那一下（§3.3），在等的接回连同留着的几样一起取消，「这一趟要录」照 §3.3 留。

**每一路各自进出**（项目所有者 2026-10-10）：开录只是打开录像意图、定下这次录哪几路；每一路的相机带着录像输出出了画面，这一路就加入。
一路的相机被拿走、断开或卡住，这一路自己收尾（文件封好）退出，别的路不动；回来了再加入。起因：车主离车时车机拿走后座舱相机，
以前整次停录、马上整次开，环视、前座舱的会话在交接途中被重建（平台笔记 §3.6「车主离车之后」）。

**录像从不动相机。**录像宿主（`MultiCameraManager`）只做三件事：每一路声明一个录像输出、告诉调度它在备 / 备好了 / 建不起来、
听调度说哪一路带着新会话出了画面、哪一路的相机走了（§5.2）。开、关、改输出、救都是调度的事（§4）。
每一路的状态（`RecordingLanes`，主线程，只有录像宿主改）：

| 状态 | 是什么 |
|---|---|
| 等着（WAITING） | 不在录：等它的相机带着录像输出出画面、录制器停放着或备好了。开录时每一路都从这里起 |
| 在加入（STARTING） | 录制器在重新备好、或者开了录还没写进第一笔 |
| 在录（LIVE） | 写进过第一笔 |

- **加入**（`RecordingLanes.joins`）：等着、录制器停放着或备好了、相机在出画面、会话带着这一路的录像输出 —— 四条都成立就重新备好、
  开录，第一个文件按此刻起名（storage-spec §3），写进第一笔才算在录。这个录像意图里第一路加入时报「录起来了」。
- **退出**：调度说这一路的相机走了（丢了、卡住了在救），或者它写不进而且是相机的事：这一路收尾（封好文件），录制器停放，
  还是同一个录像输出，相机回来后的第一份会话就带着它。别的路照录、会话不动；录像的阶段、通知、悬浮按钮都不动，不报停录。
  熄屏放开的那几路（座舱，没留着的环视，§3.3）也这样退出，亮屏、或者熄屏中哨兵模式变成开时带着它开回来，出了画面就加入。
  熄屏时还没建的录制器不建，亮屏那一轮再建。
- **录制器留多久只有一条**：录像开着、这一路在计划里，相机关着的这一路（熄屏放开的、丢了的、被拿着的）录制器就一直停放着；
  不再这样了（停了录、这一路不在计划里），调度当轮报它的录像输出「随相机关了」，录制器才放。我们关的别的情况（停录后没人要、
  保持到点、车机要睡、退出），录像输出随相机关了、录制器放掉；下一次开录另建一个。
- **一路都不在录**：录像不算停，显示「等待摄像头，恢复后自动继续」；哪一路回来哪一路自己加入，没有接回次数。
- **会话带不上录像输出**（相机层配会话失败时把它丢了）是相机那一侧的事：那一路退出，过一会儿再声明（§3.4）。不算「录制器建不起来」，不会整次停。
- **录制器建不起来**（MediaRecorder 还有开不了录）：这一个录像意图里不再录它，状态条说「X：无法录制，其他摄像头继续录制」；
  计划里每一路都这样才整次停（还没有一路加入过是 `START_FAILED`，加入过是 `UNKNOWN`）。
- **对齐**：加入的那一路第一个文件和别的路错开（名字就是它真开始的时刻）；别的路下一次切段、共用的名字一换新的，它马上跟着切、
  拿同一个名字，之后和别的路一起分段（`SharedSegmentName`、`RecordingLanes.alignsNow`）。界面上的段号只在出一个新的共用名字时加 1，
  开新的录像意图时清零。
- **代数和作废**：每次开录、停录，录像的代数 +1；每一路另带一个计数，退出一次、加入一次 +1。排着的任务（建录制器、重新备好、
  录制器的回调）带着开录时的那一代和那一路的计数，对不上就作废 —— 开 → 停 → 开两秒内，上一次剩下的任务不会打到这一次的录制器上。
- **主界面状态条**只在至少一路在录时从各路的摘要说（`RecordingLanes.hint`），界面重建、回到前台照样说对：有一路停手了、或者录不了，
  说「前座舱：无法录制，其他摄像头继续录制」；一路被占用「后座舱：摄像头被占用，其他摄像头继续录制；释放后该路自动恢复录制」；
  两路以上「部分摄像头被占用，其他摄像头继续录制；释放后自动恢复录制」；在救、在起来的不说 —— 先说错再改口，不如晚几秒说对。
  开录落定时的提示按落定那一刻真正在录的几路说（「已开始录制 N 路」），一路都没在录就说「等待摄像头，恢复后自动继续」。
- **各路都停手**（每一路都救了 3 轮没用、或者录不了）：录像照样不停，界面照样说「等待摄像头」，不加新文字（项目所有者 2026-10-11）；
  停手的一路，相机服务报它空闲、或者亮屏时解除停手、从头救（§4.8），所以「恢复后自动继续」仍然属实。这一种只进黑匣子。
- **回放**：进度条按环视排、跟着环视走；座舱录下的存着，跟着它那一段能删、能锁，只是不上进度条（ui-spec 七）。

### 3.3 熄屏

**熄屏持续录制**（2026-09-26，默认开）。为什么要有它（项目所有者，实测过的事实）：下车前打开车机自己的「哨兵模式」，车机一直醒着、
只是黑屏；这时 App 开着录像，人下车、屏幕黑了，录像照样一直录。这个选项就是为了保住这件事。它只管录：不申请唤醒、不拉住车机
（2026-09-27 重申：它只管哨兵模式）。开着时（项目所有者 2026-10-12、10-13、10-27）：

- 屏幕黑了不到 30 秒，相机一步不动，录像照常。
- 黑满 30 秒那一刻：两路座舱放开（亮屏再回来、各自接回录像）；环视看哨兵模式 —— 开或布防、正在录，环视接着录；不然环视和座舱
  同一轮放开、停录（为了车机稳定，不再追求环视录到最后一刻）。
- 之后熄屏中哨兵模式读到开或布防，环视开起来录；读到关，当场放开；车机要睡全放开。
- 在开车时环视一律不按熄屏放开。

关着时：黑满 30 秒停录，在开车也一样（项目所有者 2026-11-02）。下面是这些规矩各在哪一处判。

开发者选项「熄屏录制（阻止休眠）」2026-11-02 停用：唤醒锁那一步的代码留着备用、走不到，资料在平台笔记 §3.6，要用先问项目所有者。

#### 屏幕真黑了（项目所有者 2026-10-12，D1）

这台车上安卓的熄屏广播、`isInteractive` 只在车机下电时才变（平台笔记 §3.6「屏幕真黑了」）：车主下车、中控屏黑了，安卓还说亮着，
哨兵模式没开时要再过四到六分钟，开着时一直不变。所以熄屏看屏幕真黑没黑，整个 App 一处定义（`ScreenState.dark()`，`ScreenState`
是唯一写它的地方）：

- **熄屏** = 安卓熄屏，或者车辆说黑。**车辆说黑**（`VehicleScreen.verdict`）：屏幕电源事件说熄，并且点火在 ACC 或更低（ON、DRIVING
  是亮；没见过的码不拿来判黑）。两项读到一项就看那一项，都读不到只看安卓。亮屏时点火先到、事件晚 40–100 ms：两项「且」起来，
  开车门那一下就判亮。
- **黑着时要亮得有证据**（项目所有者 2026-10-27）：已经黑着、或者还没有车辆的判断时，点火 ACC 或更低就是黑，不管屏幕电源事件说什么 ——
  车没通电时屏幕亮了（远程开空调、远程看车这一类）照熄屏算，主界面、超级镜子、座舱都不动。点火读不到、事件说亮：照上一次算
  （约 6 秒），过了只看安卓。起因：人真回来的 13 次全是车先通电再亮屏；车一直在 ACC 时屏幕亮过 0.4 秒、60 秒，以前都当成人回来了。
  连带：人在车里、车没通电时点亮屏幕也照黑着算；进程在 ACC、屏幕亮着时起来也算黑（以后可能调整）。
- **车辆接口连着、两项一时读不到**：照上一次的判断算，最多两次对账（约 6 秒），过了只看安卓。接口没连着（在连、连不上、这台车机没有）
  当场只看安卓 —— 降级：熄屏就是安卓熄屏。
- **车辆信号一直在读**：进程一起来就登记「核心」（`Telemetry.keepCore`：只读离散信号，订阅加每 3 秒对账；不读浮点传感器、不开定位）。
  连不上的每 5 分钟、安卓每次亮屏再连一次；这台车机根本没有这套接口的不再试。连不上（含连上后断了）的那个车辆对象不再用，再连时重新建。
- **安卓刚亮的那一下不信记着的读数**：睡之前最后读到的是「黑」，拿它判的话每个早上都会当成车机自己醒了。安卓亮了先让车辆信号当场读一遍
  （`Telemetry.reconcileNow`），读回来再判，最多等 2 秒；等满了、接口没连着就只看安卓。代价：真的夜里醒、2 秒内没读回来，先算亮屏，
  读到黑再熄屏一次。
- **屏幕不知道黑没黑时不动手**（`ScreenState.known()`）：进程起来时安卓亮着、第一份车辆判断还没读到（最多等 2.5 秒）；安卓刚亮、醒来那一遍
  还没读回来（最多 2 秒）。这两段里恢复、接回录像排到知道了再做（`ScreenState.whenKnown`）；调度不开相机、不重开，关、改输出照做，
  知道了马上叫醒调度。
- **只看安卓的那几样结束不了车辆说的黑**：每 2 秒的轮询只在安卓熄屏着时跑、只认安卓亮了；主界面回到前台不等于屏幕亮着。

**四条边**（`ScreenTransitions`，纯函数），每条边按固定顺序做：

| 边 | 什么时候 | 做什么 |
|---|---|---|
| 熄屏（E1） | 亮 → 黑。平常是车辆先说黑（车主下车），安卓还亮着；进程起来时读到已经黑着的也是这一条（起点不明） | 相机管家记一笔（`CameraKeeper.screenOff`）→ 监听者：相机层叫醒调度、主界面排 15 秒退后台、超级镜子放开登记、盲区画面移走窗口 |
| 车机要睡（E2） | 已经黑着，安卓熄屏 —— 这台车上就是车机下电（哨兵模式没开时离车约 4–6 分钟后） | 叫醒调度：车机要睡由相机管家自己判（下面「车机要睡」）。监听者不叫（屏幕早就黑了） |
| 车机醒着、屏幕黑着（E2'） | 黑着，安卓又亮了，车辆还说黑（车机自己醒了一阵；车没通电时屏幕亮了也是这一条） | 叫醒调度；按开机自启动的规矩恢复服务（`Recovery.restore`），不拉界面。不开相机、不开录（醒来不算哨兵模式变成开） |
| 亮屏（E3） | 黑 → 亮：车通电了（点火 ON、DRIVING）—— 开车门；早上回到车上 | 相机管家（`screenOn`：该接的接）→ 接回因熄屏退下去的主界面（`Recovery.bringBackUiAfterScreenOn`）→ 恢复（`Recovery.restore`）→ 监听者 |

车辆信号读不到时，熄屏就是安卓熄屏：E1、E2 一起来。

#### 通道算黑：黑满 30 秒（项目所有者 2026-10-13）

屏幕黑了不到 30 秒，相机一步不动 —— 开着的接着开、输出不改、录像不分段、录制器不停放；这期间亮了，什么都没发生过。

- **一条规矩，在通道这一层**（`ChannelRules.darkForChannel`）：通道算黑 = 屏幕真黑满 30 秒（`ChannelRules.HOLD_MS`，和「保持 30 秒」同一个数、
  同一个意思：30 秒内回来，通道零变动），或者黑着时安卓也熄屏了（车机要睡）；起点不明的按满 30 秒算。车没通电时屏幕亮了还是黑，
  照常数这 30 秒。调度每一轮照它填 `World.screenOn`，预览要不要、保持、熄屏放开、亮屏解除停手、录像的事实、拍照不拍哪几路、
  录制器建不建看的都是这同一个；黑了还不到 30 秒时调度算好还差多久，到点自己醒（`ChannelRules.untilDarkForChannel`）。
- **为什么**（平台笔记 §3.6「黑一下又亮」）：车主开关车门，屏幕黑了 4.7 秒，我们关了后座舱、亮屏再开，重开 15 秒没画面；
  车机拿后座舱是在屏幕黑了 98 秒以后，30 秒还赶在它前面。
- **关着的座舱黑着不开**：屏幕真黑了还不到 30 秒时，开着、在开的座舱照旧，关着的算熄屏放开 —— 这期间来的开录、拍照只开环视。
  开着的座舱这期间卡住了也不重开（项目所有者 2026-10-27：熄屏期间绝不开座舱）：没在开车时救援对它只做重建会话，重开留到亮屏。

#### 熄屏放开相机（项目所有者 2026-10-12 D2、D4；2026-10-27）

**通道算黑时两路座舱谁都不要** —— 录像、预览、拍照、超级镜子一样不算；亮屏又都要了。为什么（平台笔记 §3.6「屏幕真黑了」）：
屏幕黑了约 98 秒后车机要拿后座舱相机。我们拿着它的 4 次，关它在相机服务里卡 5–8 秒，其中 3 次环视跟着不出画面、救了 35–43 秒；
我们不拿着它的那一晚车机拿了 6 次，环视一次没断。

**环视留不留**（项目所有者 2026-10-27，为了车机稳定：不再追求环视录到最后一刻，也不为中间不明原因的启动、亮屏去试着录）：
通道记着环视这一段熄屏是哪一种（`ChannelRules.SurroundInDark`：照亮着算 LIT、留着 KEPT、放开 RELEASED）和上一次读得到的哨兵模式，
每一轮最先判（`ChannelRules.judgeSurroundInDark`）。**环视留着** = 「熄屏持续录制」开着并且是 KEPT（`ChannelRules.surroundKept`）；
留着的环视真开起来还要录像要它（「在录」看此刻：U 盘晚到几秒、存储停了接回，录像一登记就开）。

| 什么时候 | 环视 |
|---|---|
| 亮着；黑了还不到 30 秒；在开车 | 照亮着算，不判。黑了不到 30 秒时哨兵模式变了，也等 30 秒那一下再判 |
| 通道刚算黑（起点不明的当场） | 哨兵模式读到开或布防 → 留着；读到关、读不到 → 放开（读不到算没开） |
| 之后哨兵模式读到关 | 当场放开（只认读得到的关） |
| 之后哨兵模式从不是开变成开或布防（哪个先到都算） | 留着：「熄屏持续录制」开着、录像要它，就开起来录（下面「录像在黑屏里」） |
| 哨兵模式读不到 | 不变：留着的不算关，放开的不算开 |
| 车机要睡：黑着时安卓熄屏，没在开车 | 放开，不管哨兵模式；上一次读数不动 —— 醒来哨兵模式还开着不算「变成开」，睡着时被打开的醒来读到算 |
| 屏幕不知道黑没黑 | 不变（车机要睡那一行照判） |

- **同一轮放开，环视先关，不开回来**：通道刚算黑那一轮环视没留着，就和座舱同一轮放开 —— 环视先单独关，关完座舱一起关，什么都不开回来。
  环视留着的，照「关座舱前先关环视」（§4.3）。
- **在开车**：环视不按熄屏放开、也不判，照登记表算（预览熄屏时照旧不算）；车机要睡那一行也不放开环视。不再开车时还算黑，就在那一刻判。
  座舱照旧放开。
- **记在进程这一层**：哪一种、上一次读数跟着进程，不跟着管线 —— 管线放掉重建不断熄屏录像，新的一份接着用；车机要睡那一下的放开和
  上一次读数留到醒来。进程起来时是放开、没有上一次读数：第一次读到的只当底，之后变成开才算 —— 进程在黑着时被拉起不开相机。
- **哨兵模式**读的是车辆信号核心那一份（`Telemetry.latest()`）；接口没连着算读不到。哨兵模式、在不在开车变了叫醒调度；
  「熄屏持续录制」每一轮现读。读到布防就开（实车上见过从关直接跳到布防）。
- **只有一处判断**：`ChannelRules.releasedByDark` —— 座舱：通道算黑，或者屏幕真黑了还不到 30 秒而它关着；环视：通道算黑、没在开车、没留着。
  它是 `holderWants`、`wantsKind` 开头的那一道闸；录像的事实、拍照不拍哪几路（`excludedFromPhoto`）、关的原因、诊断报告里「该开」那一栏
  问的都是它。它只看屏幕、开车、哨兵模式和设置，不看谁登记着。按「不是环视那一路」认：非极氪的自定义车型上，熄屏时除了环视别的路一律放开。
- **不为拍照开相机**：通道算黑、没在开车时拍照不算要相机，只拍本来就在出画面的那一路（一般是留着的环视），一路都没有就当场收尾。
- **关**：通道刚算黑的那一轮（调度到点自己醒），两路座舱一起关（原因 `DARK_RELEASE`）；环视还该开、此刻能用相机的，先单独关环视、
  座舱关完再开回来（§4.3「关座舱前先关环视」）。手上有一步的，照常等它做完再关。
- **录像**：放开的那几路照「退出」收尾，录制器停放着、还是同一个录像输出（§3.2）；状态条不把熄屏放开的算成被占用。三路都放开了，
  相机管家照下面的规矩当场停录，不进「等待摄像头」。
- **亮屏**：座舱又有人要了，照开的次序一路一路开（放开了的环视排在前面），带着停放的录制器，出了画面各自接回录像。
  录像输出还在备的，最多等 2 秒 —— 从这一路又要录像那一轮算。亮屏是车通电了，车没通电时屏幕亮了一步不动。

#### 录像在黑屏里（项目所有者 2026-11-02「熄屏判断收归通道调度」）

录像停不停、黑着能不能开、录制键上的小字，都照相机管家的规矩，每一样只有一个定义：`ChannelRules.recordInDark`、`startsInDark`、
`onRecordVerdict`、`darkOutlook`、`headUnitSleeps`、`driving`。调度每一轮发布（`ChannelScheduler.recordInDark`，和环视留不留同一处发、
同一道闸），决定变了相机管家排到主线程上照它停、开。

**停不停**（`recordInDark`）。通道算黑以前录像照常；之后：

| 通道算黑以后 | 录像 |
|---|---|
| 车机要睡 | 停（`SLEEPS`） |
| 熄屏持续录制关着 | 停（`SETTING_OFF`）—— 黑满 30 秒，和相机放开同一刻；在开车也一样 |
| 计划里没有环视（「计划里有环视」：在录时看这一次的计划，没在录时看启用的那几路） | 停（`NO_SURROUND`） |
| 在开车、或者环视留着 | 接着录环视（`KEEP`） |
| 其余（停着车、环视放开了） | 停（`RELEASED`） |

停的那一路先封好文件再关相机（§4.3「先停录、再释放」）。停了亮屏接不接，停的那一刻定好（`ChannelRules.resumesOnLit`）：
「熄屏持续录制」「启动自动录制」开着一个就接；进程被车机结束了也照「这一趟要录」接（§3.2）。存储一类的自动接回在等的，一起取消。

**黑着时开录**（`startsInDark`）：屏幕黑着时录像能不能（再）开起来只看这一句，不成立的说得出为什么（`ChannelRules.DarkStart`）：

| 情况 | 开不开 |
|---|---|
| 车机要睡 | 不开（`SLEEPS`） |
| 计划里没有环视 | 不开（`NO_SURROUND`） |
| 熄屏持续录制关着 | 不开（`SETTING_OFF`） |
| 通道还没算黑（黑了不到 30 秒）、在开车 | 开：关着的座舱不开，开着的录到黑满 30 秒；之后照上表录到停 |
| 通道算黑，环视放开了 | 不开（`RELEASED`） |
| 通道算黑，环视留着，这一下不是熄屏中哨兵模式变成开（恢复的例行接回、进程起来时的接回、启动自动录制、人按的） | 不开（`NO_SENTRY_RISE`） |
| 熄屏中哨兵模式变成开（布防）让通道留下了环视（`Why.SENTRY`；睡着时被打开的，醒来那一轮读到也算） | 能用相机就开，只录环视；用不了（前台服务是后台起的）不开（`CAMERA_UNUSABLE`），亮屏再接 —— 不进「等待摄像头」 |

- 存储一类的自动接回（`Why.RESUME`）不看它（§3.2）。
- 不成立的只记下「这一趟要录」，亮屏再接；记的那一行只在「这一趟要录」真的变了时写（恢复每 5 分钟例行来一次）。
- 通道刚算黑那一下没在录的，环视留着也不开（那一刻在录才接着录）。车机黑着醒了不开录；进程在黑着时起来什么都不开。
- **屏幕黑着一律不拉主界面**（项目所有者 2026-10-13，没有例外）：不为「启动自动录制」拉，也不为用不了相机拉，等亮屏。
- 人在车里、车没通电时点亮屏幕按录制键（照熄屏算）：通道算黑以后不开、只记下「这一趟要录」，界面没有新的提示（项目所有者 2026-10-27 先这样）。

**录制键上的小字**（项目所有者 2026-10-03、10-13：小字要说清车机休眠时还录不录）：录制中、等待摄像头时，录制键第三行写现在熄屏的话
这段录像会怎样，和上面同一套规矩，照此刻的车、设置推（问相机管家 `CameraKeeper.darkOutlook` → `ChannelRules.darkOutlook` →
`ScreenOffPlan`）：

| 现在熄屏的话 | 小字 |
|---|---|
| 熄屏持续录制开着、计划里有环视，在开车、或者哨兵模式开或布防（停着车时环视留着，车机也不睡） | 「熄屏后继续录制环视」 |
| 黑满 30 秒停，亮屏接（「熄屏持续录制」「启动自动录制」开着一个） | 「熄屏暂停，亮屏后恢复」 |
| 黑满 30 秒停，亮屏不接 | 「熄屏后停止录制」 |

小字看哨兵模式、在开车、计划里有没有环视、几个开关，这几样变了就重判。设置里「熄屏持续录制」的说明是项目所有者 2026-10-27 批准的那一句
（ui-text-style §9）。

**熄屏后的帧率**（项目所有者 2026-11-04；「熄屏持续录制」的下一层，默认跟随视频流配置）：环视留着只录像时，录像按选的帧率录
（10 或 3 fps；视频流配置本来更低的照低的），码率按同一条公式跟着低。为的是下车后录像文件小得多（默认画质一小时：平时约 4.5 GB，
10 fps 约 1.8 GB，3 fps 约 0.54 GB）。判断在相机管家（`ChannelRules.darkFps`、`darkFpsChange`，开录时、通道的熄屏决定变了时定），
相机层、录制器照做：摄像头和会话不动，GL 那一步隔帧，编码器按新的帧率、码率建。

- 降下来从下一段起（换段本来就换编码器，不为它多切一段）；亮屏、开车马上切一段恢复。熄屏中哨兵模式变成开、接着录环视的，第一段就按选的帧率。
- 隔帧宁可略快（提前 25% 放行，项目所有者：不用准，以系统稳定为主）。回放照真实时间，不是延时摄影。声音照常录。
- 选了熄屏后的帧率时录制走 MediaCodec（同行驶信息条，`AppConfig.shouldUseCodecRecording`）。

#### 车机要睡、在开车

- **车机要睡**（`ChannelRules.headUnitSleeps`，项目所有者 2026-11-02）：安卓熄屏了、没在开车。这台车上安卓熄屏就是车机下电
  （熄屏后 3–5 秒进程被结束或冻住）；哨兵模式开着时车机一直醒着、安卓不熄屏，所以不另看哨兵模式。调度照它：不再保持，
  手上那一步最多再等 1 秒，然后按次序关，从此只关，不开、不改输出、不救（§4）；环视放开；录像停。它不记在登记表上。
  以后找到更早、更准的「要断电」信号，只换这一处（项目所有者 2026-10-10）。
- **在开车**（`ChannelRules.driving`，项目所有者 2026-10-11）：挡位读得到、不是 P 就算 —— D 挡等红灯、走走停停都算；读不到挡位时才看车速：
  读得到、大于 0。车机只在 P 挡断电，所以挡位说了算。都读不到按没在开车算，相机赶在断电之前关。

#### 主界面

主界面在熄屏这件事上只管界面：熄屏 15 秒后退到后台（在录、含等待摄像头，或者在等开录、等自动接回时不退；到点先问一遍屏幕是不是
真的还黑着，不知道就过 2 秒再看）。熄屏那一刻主界面在前，就记下「因熄屏退下去」（`AppConfig.setUiLeftForScreenOff`，同步落盘），
亮屏时拉回来，进程被车机结束了也照它拉。熄屏时预览本来就不算有人要，不用先注销；超级镜子熄屏时只放开登记，画面留在会话里。

### 3.4 让路与再试（项目所有者 2026-11-10，次序和时机照旧）

**会话装不下时谁先让**：一张表（`ChannelRules.YIELD_ORDER`），相机层装不下时问它丢谁 —— 拍照的 JPEG → 盲区画面 → 录像中的超级镜子 → 录像；
主界面预览不让。

- **共享预览流挂不下**（`ChannelRules.sharedOverflow`）：主界面预览、超级镜子、盲区画面三块挂在一路相机的同一条共享预览流上，
  上限是相机给的（`getMaxSharedSurfaceCount`，安卓上一般 4）。挂不下只让盲区画面：第二块（`SIDE_SECOND`）→ HUD → 第一块（`SIDE`）；
  预览、超级镜子不在这里让，建流的那一块一直带着。
- **会话配不上**（`onConfigureFailed`；`ChannelRules.onConfigFailed` 给出丢什么、隔多久、同一组再试了几次）：
  1. 有拍照的 JPEG 先丢 JPEG（拍照退回抓预览帧），200 ms 后重配；
  2. 会话里有盲区画面，三块一起丢，200 ms 后重配；报给盲区画面的先后照 `ChannelRules.SIDE_DROP_ORDER`（中控屏、第二块、HUD）——
     中控屏先撤、HUD 最后，画面不来回跳；
  3. 在录像：有超级镜子先丢超级镜子，不然丢录像输出（那一路退出录像，别的路照录），500 ms 后重配；
  4. 不在录像：同一组再试 3 次（各隔 200 ms），还不行报一次错（`onCameraError(-3)`），交给救援（§4.8）。
- 丢了的那一样由相机层报给声明它的那一方（`SingleCamera.dropOutput`，原因 `CONFIG_FAILED`）。

**让了之后什么时候再试**：让掉的那一样记在相机管家的账上（项目所有者 2026-11-10「让了之后什么时候再试也由管家记、到点通知」）：

| 让掉的 | 记在哪 | 什么时候再试 |
|---|---|---|
| 超级镜子（环视、后座舱两块） | 那一块的 `CanvasSlot`（`refused`） | 重新打开窗口、亮屏、放回来、点「点击恢复」时那一方说（`retry`）；管线换了相机管家自己再试（`ChannelRules.retryOnNewPipeline`，撤回了的也算）。看门狗不试 |
| 盲区画面（三块；窗口挂不上也一样） | 那一块的 `CanvasSlot` | 这一段结束（离开 D 挡 30 秒、熄屏、原厂画面之后）那一方说；管线换了不试 |
| 录像（一路的录像输出） | `RecordRetries`（相机管家给每一份管线开一本） | 隔 12 秒再声明，到点相机管家通知；连着 3 次都带不上，等它的相机走了回来、要它的登记方变了、或者亮屏（通道算黑过的那一种亮屏）；会话带上了就清。规矩 `ChannelRules.recordRetryAfter`，和救援梯子一个节奏 |
| 拍照的 JPEG | 相机层（`jpegDropped`） | 这一路下次正常打开相机 |

- 让着的那一样再试之前不声明，不然调度会一直想把它加回去，一次次重建那一路的会话。
- 等着「相机走了回来」的录像那一路：录像开着时 RECORDING 一直让那一路开着、在出画面，相机不会走，所以登记表变了、亮屏也解开
  （和救援停手之后同样的解锁，§4.8）。
- 画布怎么交给相机管家、管线换了怎么重新交，在 §5.3。
- 记下的两条待办（项目所有者 2026-11-10：这次没改）在 §8。

### 3.5 拍照、前台服务、退出

**拍照**（`CameraKeeper.takePhoto`）：拍照键、悬浮按钮、灵动贴走同一个入口。

- 先查有没有地方存：没有 U 盘、开发者选项没开就不拍、不开相机，提示「拍照失败：未检测到 U 盘」（storage-spec §4）。
- 查过了登记 PHOTO（§3.1）：相机没开的路由调度按次序开、带一个不显示的出帧口；已经开着的路什么都不改，拍完也不摘出帧口。
  现在用不了相机（§4.7）时不开相机。
- 各路出了画面才按快门，最多等 10 秒，到点只拍出了画面的；提示按实际存下了几路说。
- 这一张不拍、不算进该拍的（`ChannelScheduler.excludedFromPhoto`，黑匣子一行）：被别的程序拿着、被另一路挡着、救了 3 轮停手、熄屏放开的，
  和这一台那一轮满 60 秒还有开或关没返回的那一路（§4.5）。在出画面的照拍，哪怕它的录像路不在录。通道算黑、没在开车时拍照不算要相机，
  只拍本来就在出画面的那一路（§3.3）。
- **「拍照使用 JPEG 输出」一直开**（项目所有者 2026-10-09）：普通用户锁成开，只有开发者选项开着时能改。关着时照片只能从主界面的预览上截，
  主界面在后台时没有预览，悬浮按钮怎么拍都拍不到画面。JPEG 让路之后退回抓预览帧（§3.4）。

**前台服务**：开不开只有一条规矩（`ChannelRules.foregroundServiceNeeded`），只有相机管家照它起停（主界面、设置、保活只请它对一次：
`refreshForegroundService`、`ensureForegroundService`）——

- **没退出，而且「开机自启动」开着、在录、或者「这一趟要录」立着**（被打断等接回、因熄屏停下等亮屏接：接回时相机是从后台开的，
  后台拿着相机安卓要求有前台服务）。
- 要的：没起就起，起着就照录像此刻的样子换通知上的字（`notificationTitle`、`notificationContent`），不为换字再起一次；不要的：起着就停 ——
  先停服务再放相机：调度看到没有前台服务，没人要的相机当场按次序关，不在后台拿着相机保持 30 秒。
- **主界面每次回到前台都刷新一次**：后台才起的那个服务被主界面在前时刷新过一次，从此也算能用相机（`CameraForegroundService.startedWhileVisible`，
  只升不降，§4.7）。安卓 12 起后台才起的前台服务用不了相机。
- 被杀、从最近任务划掉后自己拉自己、系统的 START_STICKY 重启，都只在「开机自启动」开着时做；超级镜子、盲区画面、悬浮按钮、后台录制几个服务
  的 sticky 也跟这一个开关（§6）。

**退出**（`CameraKeeper.beginExit`；项目所有者 2026-10-10 确认的次序：停录 → 登记表作废 → 调度按次序关完 → 再结束进程）：

1. 记下「用户退出了」（`UserExit`）—— 在停服务之前：前台服务的 `onDestroy` 会发保活广播，保活接收器收到就去重启它。
2. 结束进程交给看门的线程：等主界面收尾、停录收好文件、每一路相机关完、账本上没有一轮还在关（§4.5），最多「退出最多等」
   （`ChannelRules.EXIT_WAIT_MAX_MS`，最坏约 115 秒，界面早就没了；平常一两秒），到点照样结束进程，黑匣子一行写明收尾用了多久、卡在哪。
   收尾的时候应用又被打开了（主界面清掉了退出的记号），不结束进程，新打开的主界面接着用。
3. 告诉调度「退出」：从此只关，不开、不改输出、不救；登记表从此作废，直到退出的记号清掉（人又点开主界面、车机真正开机；
   `UserExit.clear` → `CameraKeeper.exitCleared`）。
4. 这一趟到头，在录的停掉、在等开录的不等；前台服务停；超级镜子、盲区画面停（它们的画布死了）；灵动贴的扫描停（交给系统的，
   进程没了系统也不停）。
5. 放管线：停录收尾，这一份换下去，调度按次序关完相机、丢掉输出，再放录制器。

界面那几件（关界面、存日志、亮屏不再拉回来）由主界面自己做，做完告诉相机管家（`Exit.uiDone`）。
为什么要等关完：进程带着没关完的相机死掉，相机服务里就剩一个没人收的句柄，下一个进程开相机全部超时，只有重启车机能解（2026-10-08 实测）。
退出后马上又开：新建的那一份管线排着，等换下去的那一份关完才换上，从来没有第二个调度（§4.1、§4.9）。

## 4. 通道调度：唯一动相机的地方

**一个通道调度（`ChannelScheduler`）是唯一动相机的地方**（项目所有者 2026-10-10）：开、关、改输出、救、重开都由它做，一次只做一步；
看门狗并在调度里。别处要相机，只登记（§3.1）、只声明自己的输出（§5.3），然后叫醒调度。

### 4.1 一个调度，一次一步

每当有变化 —— 登记表、相机回调（开好、配好、第一帧、关好、出错、丢了、开不起来、输出被丢）、相机服务的可用性、亮熄屏、输出声明、
录像输出在备 / 备好了 / 建不起来、前台服务就绪、主界面进出前台、步骤计时器、每 2 秒一次 —— 调度对比「该是什么样」和「现在是什么样」，
**一次只做一步**。几次叫醒并成一轮，只在主线程上跑；熄屏那一下所有监听者都做完了它才跑。该做哪一步全在 `ChannelRules`
（纯 Java，每一条规矩都有测试对着，`ChannelRulesTest`）；`ChannelScheduler` 只读事实、照做、写黑匣子（`ChannelSchedulerTest` 用假相机
把实车现场原样跑一遍）。一步是开、改输出、救（重建会话或重开）、关四者之一。

**只有一个调度**（项目所有者 2026-10-29）：应用一起来就装上一个调度（`ChannelScheduler.install`，经 `ChannelFacts.install`，装过了什么都不做），
从此不换、不停 —— 每一次开、关、改输出、救、重开，管线重建（§4.9）、退出，判的都是它一个。一份管线（`MultiCameraManager`）接上来拿到一个把手
（`ChannelScheduler.Pipeline`）：交它的各路、问它那几路的事实、它的相机层报来的事都经这个把手。还没有管线时接着的是一份空的：没有路，
不判环视留不留、不发通道的决定、不按 2 秒醒，叫醒照样跑一轮（退出、车机要睡、孤儿、换上）。
登记表、相机服务、亮熄屏、车辆信号叫醒调度的监听都在装上时接一次（`ChannelFacts`）。登记表和调度不合并（项目所有者问过）：
登记表五处随时写、先于管线就有、换车型也不断；合并的话每次重建都要交接「谁要」，是补丁。

- **一个接一个**：旧的那一份管线放掉（`Pipeline.retire`）就和退出一样按次序关 —— 手上那一步做完，环视单独关（最多 10 秒），座舱一起关
  （最多 30 秒），原因写「管线重建」。新的那一份排着：它的世界照建，每一轮刷新事实、认出被别的程序拿着的、放开空出来的（只做这两步，
  `ChannelRules.settleMarks`），别的不判、不动手。旧的那一份各路都关完，换上新的那一份；再来一份新的就替掉排着的那一份。
- **卡住的那一路**（项目所有者 2026-10-29「等旧管线这一步做完再算 60 秒」）：旧的那一份某一路关一直不返回，从那一路那一下开始关起满 60 秒
  才换上新的一份（最坏约 130 秒）。那一路留下当「孤儿」：账本上那一轮照旧占着那一台（§4.5），新的一份那一路不开它，别的路照常开；
  孤儿留着的时候调度留着那一份管线，录制器到「退出最多等」由那一份的兜底放掉。那一下返回了，旧的那一份才算放完。
- **跨过去的只有**：账本（进程这一层，原样）、环视熄屏留不留和上一次哨兵读数、发给相机管家的通道决定和原因（§3.3）、每台相机我们最近一次
  关完的时刻（相机服务为旧的那一份那一关说的话，换上新的一份之后 0.5 秒以内照算我们的）。别的照旧清零（项目所有者 2026-10-29：
  用不了相机的计时、上次问相机服务、亮屏时刻、前座舱只用一次的标记、手上那一步、被拿着 —— 各路是新的，相机服务的回放照样认出来）。
- **退出**也在这一个调度里：写下退出，从此只关、不开，接着的、排着的、这时才建的管线都一样，退出的记号清掉才照常开（§3.5）。
- **「正在按次序关」**（`ChannelScheduler.closingAnywhere`）为真的就是这一段：跑的那一份在为退出、车机要睡、换下去收尾，而还没都关好，
  最多算「退出最多等」。

**下一步按这个次序找**（`ChannelRules.next`，先找到的就是它）：

1. **有在途 → 等。**在途是：手上那一步（含等第一帧；救援重开关的那一半关完了，开的那一半就在这里下达）；一路正被别人接手（丢了，我们这边
   那一次关还没关完）；一台相机那一轮有一次关没返回；一路相机层手上有动作（在开、在关、在配会话）。后三种各封顶 60 秒 ——
   **封顶只管别的路等多久**：被一轮占着的那一台自己，那一轮结束之前不开（§4.5）。车机要睡时最多再等 1 秒，然后直接去关；退出照常等它做完。
   **在关的设备是在途**（项目所有者 2026-10-14）：一台还在关旧设备的相机是在途，不管它属于哪一步，那一步 15 秒到点也不放过，封顶 60 秒。
   我们按次序关的那一步不在此列：照第 2 条自己的封顶。
2. **有要关的 → 先关。**环视开着或正在开、但已不该开 → 单独关它，最多等 10 秒；否则不该开的座舱一起关，最多等 30 秒，环视还在关就先等它关完。
   要关座舱而环视还该开、此刻能用相机的，先单独关环视（§4.3「关座舱前先关环视」）。关不等安静。退出、车机要睡时到这里为止：
   不摘死输出、不改、不开、不救。
3. 有一路丢了、开不起来还没判 → 等判完（§4.6）。
4. **会话里有死输出 → 摘。**一次一路、环视先。排在开前面，因为画面被系统收走的要马上减（§4.4）；但它也要等安静（项目所有者 2026-10-11）。
   本会话没出过画面的那一路不摘，留给第 7 条重开时丢掉。
5. **开**（要安静、能用相机、屏幕知道黑没黑）：按开的次序（环视 → 后座舱 → 前座舱），第一路该开、没开、没被拿着、没被一轮占着、不在救援梯子上的；
   被拿着的、被一轮占着的跳过，不挡后面。用不了相机、屏幕不知道黑没黑时这一路先不开，记下等什么，接着往下看改输出、救，都没有才等。
   带着它要的输出开，一样都不要就带出帧口。它有录像要、录像输出还在备 → 先等，最多 2 秒（从录像登记起算），等的时候后面的路也不开。
   出第一帧、出错、或者满 15 秒，这一步算完；满 15 秒没出画面就先往下走，由救援接手，算第 1 次。
6. **改输出**（要安静）：缺了要的输出、或者该出帧却没有一个活输出的那一路，环视先。配好并出第一帧、或者满 15 秒，这一步算完。
   **只改本会话出过画面的会话**（项目所有者 2026-10-14）：没出过画面的不改输出、不摘死输出，由救援重开时带上现在要的输出 ——
   一帧不出的会话没有东西可等完，那一下改会话会卡满 4.7–4.9 秒、报错、再关一次设备。
7. **救**（要安静；重开还要能用相机、屏幕知道黑没黑，黑着没在开车时座舱不重开；重建会话不要）：§4.8。
   **重开 = 调度下达关、再下达开**（项目所有者 2026-10-29；`ChannelRules.Half`）：这一路手上有设备的，这一步先下达关（这一路记成在关）；
   关完、账本上那一轮结束、离下达关满 300 毫秒，同一步里再下达开（带着救援的那几样，`SingleCamera.OpenKind#RESCUE`）—— 不另起一步。
   关完时该开的样子不在了（退出、车机要睡、管线换下去、没人要了、用不了相机、屏幕不知道黑没黑、黑着没在开车的座舱，`ChannelRules.reopenBlocked`），
   开的那一半不再下达，这一路关着，交给平常的规矩。两半之间那一下这一路关着，可它还在我们的一步里：相机服务这时说的话算我们的。
8. 都没有 → 空闲。

**安静** = 相机服务 3 秒内没报过别人引起的变化。相机服务的每一声分两类（`CameraAvailabilityWatch.classify`）：我们在这一路有开或关在途
（开好、关完之后 0.5 秒以内也算；丢了之后的那一次关也是我们的关）→ 我们引起的；其余 —— 包括我们稳稳开着时它报的「空闲」，那正是交接时的乱报
（平台笔记 §3.6）—— 算别人引起的。只看别人引起的。

### 4.3 开和关

**环视单独开、单独关：它开、关的时候座舱不动**（开的次序 2026-10-08 定；关 2026-10-09 定）。实测（2026-10-09，16 次关相机对下一次打开）：
环视比座舱先关完的 4 次，下一次打开都正常；环视最后关完的 11 次里 9 次那一次关要 4–17 秒，下一次打开它会话配好却一帧不出，要重开设备，
其中一次一直坏到重启车机。只开环视时它开、关的时候没有别的相机在动，开关各 0.1 秒、从来不出这种事。
例外：一路被拿走、放开后由调度单独开环视时，两路座舱可能正开着、在出帧 —— 只动它一路、座舱不动，「一次只动一路、环视单独动」照样成立。

**关座舱前先关环视**（项目所有者 2026-10-15）：一句规矩，只在 `ChannelRules.closeStep` —— 计划里要关座舱（熄屏放开、保持到点、没人要），
环视开着或在开、还该开，此刻能用相机（`ChannelRules.usable`），没被拿着、不在救援梯子上 → 这一步只关环视（原因 `SURROUND_FIRST`，
环视单独关的 10 秒封顶照旧）。下一轮环视关着了，座舱一起关；再下一轮「开」那一步把还有人要的环视照常开回来。不另立计时、常数、动手的地方：
**通道调度照旧是唯一动相机的地方，登记表照旧是唯一记谁要相机的地方**（项目所有者原话：「一切仍然以『通道调度』为唯一的管理，包括那个登记册为
唯一的登记使用情况。」）—— 开回来靠的是登记表上本来就要它的录像、超级镜子、盲区画面、预览。

- 不走这一步的：此刻用不了相机（环视关了开不回来，座舱照旧在它旁边关）；环视自己不该开了（照旧它先关，不开回来）；环视只在保持、座舱先到点
  （先单独关它，它的保持跟着结束）；环视在救援梯子上；不是计划里的关 —— 救援重开时关旧设备、丢了之后那一次关、车机拿走那一路；
  退出、车机要睡时环视本来就先单独关。
- 录像：环视那一路照「退出」收尾，录像还要它就停放录制器（同一个录像输出），开回来出了画面再加入；超级镜子、盲区画面、预览的画布声明不动，
  开回来带着。救援梯子一次都不算，也不算「丢了」。
- 代价：每一次计划里的关座舱，环视（含环视录像）断约 0.5–1 秒、录像多切一个文件；开着的超级镜子闪一下、显示着的盲区画面黑一下；
  只在保持的环视保持提前结束。开回来失败一次（15 秒没画面、救援接手）要 21–46 秒。
- 为什么（平台笔记 §3.6「放开座舱时环视跟着断」）：环视开着时关座舱，之前 20 次里环视跟着停了 8 次，都停在一个座舱关完的那一帧前后，
  救了 40–50 秒；「先关环视、再关座舱、再开环视」同一个进程 23 次、退出再开 21 次都正常。

**先停录、再释放**（项目所有者 2026-11-02）：要关的那一路，录制器还在写文件（在录，或者叫停了还没封好）的，关之前先收尾 —— 调度叫录像那一侧
让这一路退出录像、封好文件、录制器停放，相机照常开着出画面；封好了再照原样关，停放着的录像输出挂在会话里一起关，不为它多重建一次会话。
最多等 5 秒，到点照常关，录制器自己接着收。收尾时这一路不算能用，录像不在它上面再加入；收尾中又不关了（亮屏了、又有人要了），
录像照常加入、开一个新文件。规则在 `ChannelRules.sealFirst`，一处；只开预览、超级镜子、停了录的关都走不进来。
为什么：熄屏放开时关相机和停录同时开始，相机 0.1 秒关好，文件 0.3–0.7 秒后才封好；手动停录本来就是先封好文件、过后才关。

### 4.4 输出：减输出能拖就拖（项目所有者 2026-10-10）

- **输出按消费者认**（`ChannelRules.Out`）：预览画布、超级镜子画布、盲区画面画布、录制器的输入 SurfaceTexture，加上一个不显示的出帧口
  （只用来补位：一路要出帧、会话里却没有一个活着的输出能出帧时才加）。同一块画布再声明一次还是同一个输出，不算变化。
  拍照的 JPEG 输出常驻会话，不进这张表。
- **声明不重建**：各方声明、撤回自己的输出（画布经相机管家，§5.3；录像经录像宿主），只叫醒调度；关相机只清会话和设备，不清声明。
  会话只按调度给的那一组建（外加 JPEG），带着录像输出才用录像模板。
- **要的输出** = 有人要（登记表照 §3.1 算）、已声明、消费者还活着。加输出要的时候加。声明着、没人登记的不进会话。
- **不要了、但还活着的输出留在会话里**，到下一次本来就要动这一路、或者关相机时一起摘（改输出时多余的顺带摘掉）。要的一样都没有、
  这一路又还要出帧（在保持、只为拍照开着）时，留着的活输出就是它的出帧口，照留 —— 停放的录像输出这样撑住保持，下一次开录直接沿用；
  「停录 → 保持 → 关」整个过程，会话一次都不改。
- **死输出（消费者被系统收走）马上摘**（§4.1 第 4 条）：会话里一个消费者死了，那一路整条重复请求停下（平台笔记 §3.1.2），预览和录像一起停。
- **画布被系统收走时由我们留住**：主界面重建、关超级镜子、盲区画面的窗口移走时，画布交给管线留着，新视图接回同一块 —— 同一个输出，
  通道零变动、录像不断（§5.3）。最小化不收画布：安卓 12 的 `TextureView` 只在离开窗口时放掉 SurfaceTexture，所以最小化时预览输出成了
  「留着的」，通道零变动。
- **代价**：留着的输出照样收帧 —— 停录后环视照样往停放的录制器送帧，熄屏时留着、不画的超级镜子也照样收帧，直到下一次本来要动、或者关相机。
  SurfaceTexture 的输出不会卡住相机（平台笔记 §3.1.2）。
- **调度之外唯一允许的相机调用是请求级的**：画面调节只改重复请求，不改会话、不改输出，在这一路的相机线程上做，这一路有一步在途时先不做、
  下一次建会话时带上最新的参数；拍照只往常驻的 JPEG 输出发一张静态请求。

### 4.5 轮次和账本：关没返回、开没返回都不再开（项目所有者 2026-10-28、10-29）

**规则**：我们上一次关一台相机（或者开它）还没返回，App 里谁都不开它 —— 开、救援的重开、重建出来的新管线都算 —— 直到那一下返回、或者进程结束。
**不设时限**。相机服务说它「空闲」只记黑匣子，不放行。进程里同一台相机永远不会有两个句柄。

- **为什么「空闲」不算数**（平台笔记 §3.1）：同一个进程里问相机服务只是读本进程的缓存，只有进程第一次连上相机服务、相机服务挂了重连之后
  才是它现答；可用性回调只在「空闲 ↔ 不空闲」翻转时来；实车上车机拿走一台相机的同一毫秒，我们还开着、在出画面的另两台被报「空闲」。
  反过来，`close()` 是同步的：相机服务那边断开做完才返回，相机服务挂了也返回；进程结束，相机服务替我们断开。所以只认我们自己那一下返回，
  或者进程结束。
- **一轮**（`CameraRound`）：一份相机对象为一台相机走的一次设备生命周期 —— 从调度下达开起，到它唯一的一次「结束」为止；一轮里只有那一次开，
  一条它自己的相机线程。三样都成立的那一下才结束：那一次 `openCamera` 没在等回调；这一轮拿到过的每一个设备对象都关完了（关了之后才开好的
  那一台也就地关掉）；没有一次关在做、也没有一次开还没进 `openCamera`。一次关、一次 `openCamera` 卡在相机服务里 ⇒ 这一轮永远不结束 ⇒
  这一台到进程结束都算占着。这是规矩，不是毛病。救援的重开是两轮（§4.1 第 7 条）。
- **常备指令**（项目所有者 2026-10-29）：相机层每一次开、关、改会话都是调度下达的；自己动手的只有两样，都是调度下达开的时候就定好的，在这一轮的
  相机线程上照做、不等主线程：挂着的那一台**丢了**（被断开、报错）—— 先报、再关（`SingleCamera.lose`）；下达了关之后才开好、才报错的那一台
  （**晚到**）—— 就地关掉（`SingleCamera.closeLate`）。两样都在那一轮里，关返回之前谁都不开这一台。
- **账本**（`CameraRounds`）：进程里每台相机此刻还没结束的那一轮；只在主线程上改，退出的看门线程也能读。每一轮记着谁下达的（哪一份管线的哪一路）、
  第几轮、什么时候下达、此刻在开 / 开着 / 在关 / 在丢、从什么时候起一直有开或关没返回。下达开之前看账本：这一台有一轮还没结束就不下达，
  谁的都算。还记着这一台我们最近一次关完的时刻（`CameraRounds.closedAt`）：相机服务为这一关说的话 0.5 秒以内算我们的。
  相机服务那边算不算我们占着这一台，只照账本答。
- **谁都不等谁**：相机层不在任何一条线程上等别的线程做完；开在途时再来的开一律合并掉。主线程从不等；关相机那一下的兜底另起一条线程，
  绝不在主线程上进相机服务。
- **调度像「被拿着」一样跳过它**（`ChannelRules.camHeld`）：不开（不挡后面的路）；关着、在开的不救、不计救援次数；开着的只许重建会话、不重开；
  关座舱前不先关它。不因为它去问相机服务。相机层的开照账本再看一次，是断言：走到了不开、黑匣子记一行。
- **别的路**（项目所有者 2026-10-28：照以前）：头 60 秒照「在途」等它，满 60 秒不再等，照常开、录。
- **那一路**：满 60 秒还有开或关没返回、它还有人要、设备不在我们手上（`ChannelRules.heldByClose`）—— 录像那一侧不再算它在起来；别的路在录时
  状态条说「后座舱：无法录制，其他摄像头继续录制」（项目所有者 2026-10-28）。60 秒以内照旧算在起来：平常退出又马上打开，那一次关一两秒就返回，
  录像不闪一下「等待摄像头」。返回了照常开，救援梯子照旧。
- **代价**：一次关、一次打开永远不返回，那一路这个进程里不再开，直到 App 重启（相机服务那一侧卡死的仍要重启车机，平台笔记 §3.1.1）；
  卡住的相机线程挂到进程结束（一台相机最多一条）。平常（记录里每一次关都返回了，最长 21.4 秒）什么都不变。
- 还不做的：被拿着的一路一句「空闲」就放开（项目所有者定了保持现状）。

### 4.6 被别的程序拿走：只问、不开（项目所有者 2026-10-10）

别的程序拿走相机、相机服务把我们断开时，我们没有选择权 —— 谁拿得到由相机服务按进程优先级定（我们在前台它开不了，我们在后台就是我们被踢）。
能做的只有被踢之后的表现：

- **先报、再关**（所有错误码都这样）：被断开、出错的那一刻先报上来 —— 这一路进「正被别人接手」，算在途，别的路都不动；录着的话这一路当场退出录像
  （§3.2）—— 然后才在相机线程上关设备。
- **关完才判**（`CameraTaken.judge`，丢了和开不起来共用一个判法）：我们这边关完，再等 300 毫秒，相机服务那几声这时都到了；还有别的丢失在关的，
  等全部关完一起判，先判出被拿着的。按顺序：
  1. 这一路不在 —— 相机服务的缓存里没有它、问的时候回放里也没有，或者开的时候它不在相机列表里 → **被拿着（TAKEN）**（车机拿走后座舱时
     就是这样：相机服务一声不吭，开的时候列表里干脆没有它）；
  2. 现在用不了相机（`onError` 3、`CAMERA_DISABLED`）→ 按时间判（§4.7）；
  3. 相机服务从没说过话（容器没把可用性回调转过来）→ 普通故障，照救援的节奏救；
  4. 相机服务对这一路说的最后一句不是「空闲」→ **被拿着**：我们这边已经关完了，它还被占着，只能是别人；
  5. 最后一句是「空闲」、原因属于「被占用」一类、而另一路被拿着 → **被挡着（BLOCKED）**：两台在相机服务里冲突，它自己空着却开不起来；
  6. 其余 → 普通故障，按救援的节奏救。

  「被占用」一类：被断开；`onError` 1、2；`CameraAccessException` 的 CAMERA_IN_USE、MAX_CAMERAS_IN_USE、CAMERA_DISCONNECTED。设备错误 4 不在这一类。
  「最后一句」不论多早说的（项目所有者 2026-10-11）：AOSP 对「空闲 → 空闲」不再回调（平台笔记 §3.1）。同一次交接里因「被占用」一类断开的
  另一路直接判被挡着，一次也不试开（试开在前台可能把对方挤掉）。
- **主动认**：我们既没开、也没在开这一路，而相机服务说它不在、或者被占用、不是我们 → 直接判被拿着，不碰。冷启动时车机还拿着后座舱就是这样
  （相机服务的回放在管线构造时就收全了，调度第一眼就看得到）。「被占用（我们开着）」是不是我们按此刻判：只在这一路刚关完、这一台我们刚关完
  0.5 秒以内、或者这一台被一轮占着时算我们的；过了这些，关着的这一路还被占着，只能是别人。
- **只问，不开**：被拿着、被挡着的那一路有人要时，每 30 秒问一次相机服务它空没空 —— 登记一个新的可用性回调、收它的回放（进程里的缓存，
  不进相机服务、不开任何相机）；回放和我们的记录对不上的照回放改。它刚变成有人要、而上一次问已超过 30 秒时马上问；相机服务说访问优先级变了
  （我们回到前台）也马上问一次，但绝不因此去开。不试开：试开在前台可能把原厂功能挤掉。
- **放开**：被拿着的，等相机服务说它「空闲」（被拿着以后说的那一句，而且它在）；被挡着的，等再也没有被拿着的路。放开以后等安静 3 秒，
  按开的次序单独开，救援梯子从头算。
- **争用和嫌疑应用**：判成被拿着的，按丢的那一刻记争用、查嫌疑应用（平台笔记 §3.1）；主动认出的不查。
- 被拿着的那一路：录像里它不在录、别的路照录（§3.2）；超级镜子「点击恢复」接不上时说「摄像头被占用，暂时无法打开」；拍照不拍它。

### 4.7 能用相机（项目所有者 2026-10-10）

- **能用** = 主界面在前；或者前台服务是在主界面在前时起的、或那时刷新过（`CameraForegroundService.startedWhileVisible`，只升不降 ——
  AOSP 12 对已经放行的服务不再收回）。安卓 12 起后台才起的前台服务用不了相机，所以主界面每次回到前台都刷新一次前台服务（§3.5）。
  相机管家开录时读的是同一对事实（`MultiCameraManager.cameraUsableNow`）。
- **不能用时**：不开、不重开、不计次数（重建会话不用开相机，照做），黑匣子一行「通道：现在用不了相机（…），先不开 X」，只在变了时写。
- **开的时候相机层报「用不了」**（错误 3、`CAMERA_DISABLED`）按时间判（`ChannelRules.applyVerdict`）：判的时候主界面不在前、出事以后它也没回到过前台
  → 记下，主界面回到前台才清；出事以后主界面回到过前台 → 不用再等，照常开；主界面一直在前 → 按普通故障走梯子，有次数、会停手。
- 这样关着、开不了的一路，录像那边不算它在起来：录像是「等待摄像头」，不是「准备中」（§3.2）。
- 屏幕亮着、要录像而现在用不了相机时，相机管家先把主界面拉起来（§2.5）；黑着一律不拉。熄屏中哨兵模式变成开、要开环视而用不了相机
  （进程被车机结束过又在后台被拉起）：照这一条不开，不另想办法（项目所有者 2026-10-27：App 起不来就没有后续）。车机睡过、进程只是冻住
  没被结束的，醒来照样能用相机，这条路要保住。

### 4.8 救援（一套）

- 只救有人要（保持不算）、没被拿着、丢了判成普通故障或者开着 8 秒没进展的路；先救环视。
- **梯子**（`CameraLiveness`）：第一次救、本会话出过画面就重建会话（便宜），否则重开；12 秒一次，3 次不成歇 60 秒，3 轮之后停手。
  开那一步开不起来、满 15 秒没画面，算梯子的第 1 次。「本会话出过画面」和改输出、摘死输出用的是同一个定义（`ChannelRules.framedSession`）：
  没出过画面的会话只重开，重开带上现在要的输出。只看帧，不看相机的状态标志。
- 重开是调度先下达关、关完再下达开（§4.1 第 7 条），梯子上算一次；关的那一半关完时该开的样子不在了，开的那一半不再下达，那一次照旧算过。
- 这一台被一轮占着、或者这一路手上那一轮的开或关还没返回，返回之前不救、不计次数（§4.5）—— 这时重开只会被合并掉，梯子却白算一次。
- **停手之后**：要它的登记方变了（只解除要它的登记方变过的那一路：盲区画面随挡位登记、放开，只算环视变了，停手的座舱不为它重开）、
  相机服务报它「空闲」、或者亮屏（通道算黑过的那一种）就解除停手、从头救（项目所有者 2026-10-10、10-11、10-20）。录像开着时 RECORDING 一直登记着，
  登记表不会自己变，只等它的话，各路都停手之后录像会一直等下去。
- 帧回来了、或者这一路没人要了，梯子归零。
- **屏幕不知道黑没黑、黑着时的座舱**（项目所有者 2026-10-27）：屏幕不知道时的每一路、屏幕真黑着而没在开车时的座舱，救援和「现在用不了相机」一样 ——
  不重开、不计次数，只许第一次的重建会话。熄屏期间绝不开座舱，救援也不例外。
- **救援只有一套**（项目所有者 2026-10-09：「获取打开，关闭退出，仅此而已」）：相机报错、被断开只把设备关掉、报上来，要不要再开、什么节奏
  只有调度判。
- **同一路相机同一时刻只有一个动作在途**（项目所有者 2026-10-08）：这一台有一轮还没结束就不下达新的一轮（§4.5）；手上那一轮的开还在路上，
  再来的开合并掉，不设时限。起因：重连那一次打开还没回来，看门狗又开一次，相机服务把先开的那份踢掉，自己顶自己，直到 ANR（2026-10-08）。

### 4.9 管线属于应用（项目所有者 2026-10-10）

- **相机管线只在 `CameraManagerHolder` 建**，主界面只是登记表里的一个需要方：它向相机管家要管线（`CameraKeeper.pipeline`），只交自己的画布、
  挂自己的回调。主界面销毁不放管线，
  只交出画布、摘掉自己设在管线上的回调；相机关不关交给调度。管线建好的那一刻由 Holder 交给相机管家（`CameraKeeper.pipelineCreated`）。
- **生效的配置只有一份**（项目所有者 2026-10-30「回到主界面时生效」）：现在这一份管线照的那份 —— 车型、选的哪份视频流配置、那份里开了哪几路和
  每一路的参数、摄像头映射（`CameraManagerHolder.effective`）。录像录哪几路、各路参数和尺寸、各格的摆法、状态条上的配置名都问它
  （`RecordSpecs.effectiveProfile`、`enabledCameraKeys`）。设置页编辑的是存下的那份；回到录制界面那一刻，主界面照存下的重新摆，摆好之前
  存下的配置生效（`CameraManagerHolder.commitForMainScreen`）：建管线、录像用到的变了（`Shape.pipelineKey`）就换管线；只是名字、摆法变了，
  管线不换。在设置里改几项都只换一次。
- **什么时候放掉重建**（`CameraManagerHolder.Rebuild`）：退出；配置变了（`CONFIG`，只在主界面照存下的配置摆好录制界面时）；上一次列相机出错
  （`LISTING_FAILED`，谁来要都重建，两次之间至少隔 10 秒）；超级镜子要后座舱而管线里没有（`MIRROR_CABIN`，谁来要都重建，照生效的配置加上后座舱）。
  只为超级镜子建、现在没人要的后座舱和配置变了一样，主界面要存下的配置生效时去掉。别的调用方一律照用生效的那一份，不因为配置变了重建。
  在录的话那一段到头（`UNKNOWN`）、在新的一份上自动接回（§3.2）。
- **放掉重建了**：Holder 告诉挂着的监听者（主线程）。相机管家等新的一份建好，把交着的画布声明上去、再在同一下告诉各方照自己的规矩再登记
  （§5.3）；主界面在前当场把界面的回调接到新的一份上，在后台的回到前台时接。放掉、重建在唯一的那一个调度里一个接一个（§4.1）。
- **主线程不进相机服务**：相机列表、合成流探测、照配置定尺寸在建管线的那条线程上做；各路的画面尺寸由各自的相机线程不开设备先算
  （`resolveSize`）；相机参数在相机打开时记进 `CameraCapabilities`，主线程只读缓存。
- **槽位照存下的映射建**（`ZeekrMultiPlan.choose`，按车型存在 `AppConfig`）：相机列表完整时照列表分；不完整时照存下的建 —— 列表里少的那一路照样建出来，
  交给调度判「不在」（被拿着）。车机拿着后座舱时它就不在列表里，照列表分的话后座舱这一格就没了。只在值得时更新存下的；没存过（第一次装）照列表建
  —— 第一次装又正好有一路被拿着时会少一路，要等下一次冷启动才补上（已知的风险）。

### 4.10 谁动相机（项目所有者 2026-10-14：「必须按照统一的“通道调度”进行管理，不能在非控制的情况下由别的代码自行操作」）

| 动相机的那一下 | 谁触发 | 归调度管吗 |
|---|---|---|
| 开、改输出（含录像换输出前停送帧）、救援的重建 / 重开、关 | 调度的一步（`LanePort` 是唯一的调用方） | 是；每一次开下达一轮（账本），相机层再看一眼账本，是断言；重开是调度下达关、再下达开 |
| 会话配不上的重试、旧会话关完再建、作废在途配置 | 调度那一步里相机层的接续 | 是；算在途（`isBusy`）；丢什么照 `ChannelRules`（§3.4） |
| 被断开、报错之后的关（先报、再关） | 相机服务的回调 | 是：常备指令（§4.5）；关之前报给调度，关返回之前谁都不开这一台 |
| 晚到的设备就地关 | 那一轮那一次 `openCamera` 的回调 | 是：常备指令；关完那一轮才结束 |
| 拍照（往常驻 JPEG 输出发一张）、画面调节（换重复请求的参数） | 拍照、画面调节窗口 | 请求级，不改会话；相机线程上发，这一路有一步在途时都不发（拍照改抓预览） |
| 主界面、超级镜子、盲区画面的画布被系统收走 | 界面销毁、窗口移走 | 交给会话里还带着它的那一份管线，离开会话才放（§5.3；「带着」算到那一次关真正关完） |
| 卡顿监测（`StallWatch`） | 计时 | 不动相机，只读、只写报告 |
| 退出等满「退出最多等」还没关完：放录制器、结束进程 | 退出的看门线程 | 调度自己的封顶到了之后的兜底 |
| MediaRecorder 录制（开发者选项）停录时放掉录像输出 | 停录 | **不归**：会话里的输出死了，调度事后摘 |

## 5. 执行方

执行方只照调度下达的一步做，把发生了什么报上来；不自己决定开关、不自己重试。

### 5.1 相机层（`SingleCamera`）

一台相机一份：打开设备、建会话、出帧，一轮一条相机线程（§4.5）。

- **会话怎么建**：只由调度的一步发起，只按调度给的那一组输出建（外加常驻的拍照 JPEG），带着录像输出才用录像模板。旧会话关完再建
  （HAL 不许一个 Surface 同时绑两条流，所以每次改输出都要配两次 HAL，平台笔记 §3.1.2）。一步里的重试不往外报，一步只报一次结果。
- **共享预览流**：主界面预览、超级镜子、盲区画面三块挂在同一条预览流上（surface sharing），上限是框架给的
  （`getMaxSharedSurfaceCount`，AOSP 是 4；车机上第一次建会话时黑匣子记一行实际是几）。挂不下、配不上时丢什么照 `ChannelRules`（§3.4），
  丢了的报给声明它的那一方（`dropOutput`，原因 `CONFIG_FAILED`）；碰上 Surface 被放掉时，只摘掉真死了的那几个、报出来、同一步里再试。
- **改输出时有一路录像输出要换成另一个**（MediaRecorder 分段），先停止往旧的送帧、再重配；只停它，不停整条重复请求。
- **报的事实**：开好、配好、第一帧、关好、出错、丢了、开不起来、输出被丢、这一份会话里带着哪几样（`sessionOutputs`，快照）。
  会话不带录像输出、或者相机那一侧配不上，是相机的事，不算录不了（§3.2）。
- **常备指令**：丢了先报再关、晚到的设备就地关，都在那一轮里照做（§4.5）。除此之外不自己开、关、重开。

### 5.2 录制器

**一路一个录制器**（编码录制，默认）：开录时每一路照当时的设置定下录法和源尺寸（视频流配置、行驶信息条、左上角那行字、强制 H.264、水印、
熄屏后的帧率），一个录像意图里不变：录到一半改了设置，从下一次录像起生效。源尺寸用 `SingleCamera.resolveSize` 不开设备先算出来的那一个；
这一路不在（车机拿着它）算不出来，等它回来算出来再建。有停放着的、录法和源尺寸都一样就沿用（会话不动），否则在单独的一条线程上另建一个。
建好了声明录像输出（消费者是录制器的输入 SurfaceTexture：停放、重新备好都是它，一辈子不变），告诉调度它备好了。

- **停放**（`CodecVideoRecorder.park`）：放掉编码器和它的输入 Surface，EGL 和输入 SurfaceTexture 留着、照常取帧 —— 还是同一个录像输出，
  相机回来后的第一份会话就带着它，加入时再重新备好（再建编码器）。重新备好没成才换一个新录制器，旧的等调度报告它离开了会话再放。
- **写不进先换盘，不停录**：录制器每 5 秒把文件 fsync 一次；写入或 fsync 一报错、新文件开不出来，就立刻换到另一个挂着的盘接着写。
  内存里一直留着最近 15 秒的已编码画面（没确认落盘的留更久，上限一分钟 / 64 MB），先补写进新文件再接着录，掉盘前后的画面不丢。
  换盘顺序：设定的盘（它回来了就回去）、其余 U 盘按剩余空间、开发者选项打开着时最后是内置存储（storage-spec §4）。写在设定的盘以外时，
  每开一个新文件先看设定的盘挂着没有，挂着就写回去；状态条一直显示「已改为录制到 …（… 不可用）」。没有别的盘可换才报写不进（§3.2）。
- **写文件不在编码线程上**（项目所有者 2026-10-08）：每一路两条线程 —— 编码线程只画帧、取编码器输出，每个样本拷出来排进内存队列；
  写入线程独占 MediaMuxer：开文件、开轨、写样本、每 5 秒 fsync、收文件、换盘补写、抢救，和样本排在同一个队里按顺序做。
  排队上限约 3 秒的画面（字节按这一路的码率算，夹在 4–24 MB 之间）；满了编码线程先等 50 毫秒，还满就不编这一帧 —— 已经编码的一个都不丢。
  排队和「内存里的最近 15 秒」是同一份数据（`SampleRing`），什么算落盘只看写入线程真做过的 fsync。
- **停录分两步，几路一起**：先在停录那一刻每一路都叫停（不再录、不再分段、不再恢复或重建），编码线程排空编码器（最多 2 秒）、把「收文件」排在最后；
  再一起等写入线程写完、写文件尾、fsync、关好。几路共用一个期限 9 秒（开机时长，不含深睡），到点还没收好的（盘多半没了）不再等：内存里没确认落盘的
  交给一个抢救线程尽力写到别的盘上。期限比相机管家的收拾期限（20 秒）的一半还短。
- **已知的限制**：分段交界换编码器时不发结束流，编码器里还在路上的最后 1–3 帧随旧编码器丢掉；断电最多丢最后约 5 秒（fsync 的间隔），
  U 盘慢的那一阵再加上排着还没写的（最多约 3 秒）。开了文件、一直没开轨的是空文件，收文件时删掉、不报。
- **U 盘写入跟不上**：排队满了的那一段，黑匣子记一行排了多深、满了多久、至少丢了几帧，并提示「U 盘写入速度跟不上，录像可能丢帧」——
  一次录像最多一次，两次至少隔 30 分钟（`CameraKeeper.SLOW_WRITE_NOTICE_GAP_MS`）。不停录、不算打断。写的不是 U 盘时不提示。
- 录制器的回调带着开录时的代数：停过录又开了之后，上一次的「写不进」「跟不上」「分段」「换盘」「第一笔数据」不算数。

**MediaRecorder 模式**（开发者选项，保留，不是默认）也按路进出（`VideoRecorder`），也从不碰相机。和编码录制不一样的地方都出在 MediaRecorder 本身：
不能停放（停下的 MediaRecorder 不再取帧，留在会话里那一路整条重复请求会停，平台笔记 §3.1.2），所以停了就放、交出去的 Surface 一放，调度马上摘；
文件名在备好时就定了，所以只在这一路的相机在出画面、或者正要开时才备 —— 文件名可能比第一帧早几十秒（§8）；分段要换一个新的 MediaRecorder，
新的 Surface 声明进来、旧的不再声明，调度那一步「改输出」先停止往旧的送帧，再重配。

### 5.3 画布（`CanvasSlot`，相机管家 3c，项目所有者 2026-11-10）

主界面每格预览、超级镜子两块（环视、后座舱）、盲区画面三块（中控屏两块、HUD）各有一个画布位置，那一方建一次（`CameraKeeper.canvas`）、
一直拿着，走的时候关掉。那一方只做四件事：

- **交**（`offer`）：画布就绪了交上来。同一块再交一次什么都不变、不叫醒调度 —— 看门狗每两秒、亮屏、放回来都会再交。相机管家把它声明在
  当下那一份管线的这一路上（还没有管线就建）；换了一路相机（管线换了）或者换了一块画布，先从原来那里撤回。这一路此刻没有相机，交上来的记着，
  那一方照旧过一会儿再交；这一回不带它（§3.4）的，不声明、等再试。
- **撤回**（`withdraw`）：不用了（窗口移走、服务退出、换出这一档）。撤回不碰会话 —— 画布还活着就是「留着的输出」（§4.4）。
- **留下**（`keep`）：画布要被系统收走了（`onSurfaceTextureDestroyed`），撤回，交给会话里还带着它的那一份管线留着（`MultiCameraManager.keep`，
  调度找：接着的、换下去还在关的、孤儿）；回调返回 false，TextureView 不放。没人接回的，等它离开会话由调度放。关掉了的位置也照样能交。
- **接回**（`takeKept`）：新视图要接回上一个视图留下的画布（第一次画之前）：从管线那里拿回来，`TextureView.setSurfaceTexture` 接上，接着交。
  接不上就再留下，交不出去就放掉。

用在哪里：

- **主界面重建时预览画布留住**（项目所有者 2026-10-11）：换日夜模式、换语言、从最近任务划掉，新界面在 `onCreate` 里接回同一块 —— 同一个输出，
  通道零变动、录像不断。重建时 `onPause` 不放 PREVIEW，留给新界面。
- **关超级镜子时画布也留住**（项目所有者 2026-10-11）：窗口移走时画布交给管线（按路留：环视一块，「后视 + 后座舱」时后座舱也一块），
  关超级镜子时那几路（含环视的录像）一步不动；新开的窗口接回同一块。贴边、熄屏只放开登记，画面留在会话里，放回来时画面马上就有，不重建。
- **盲区画面的窗口移走时画布也留住**（项目所有者 2026-10-16）：下一次挂窗口接回同一块。备着时窗口透明、画布不画，画面照样留在会话里。

相机管家替各方做的：

- **记账**：声明在哪一路相机上、那一路属于哪一份管线、这一回带不带它（`refused`）。相机层丢了它（`CONFIG_FAILED`）就记下、撤回、告诉那一方
  （`Listener.onRefused`：超级镜子写一行黑匣子；盲区画面移走窗口）；再试的时机照 §3.4。
- **声明到了一路相机上**（第一次、换了一块画布、管线换了）告诉那一方（`Listener.onBound`），那一方照它摆画面（拨回缓冲区尺寸、画面尺寸）。
- **管线换了一份**（`CameraKeeper` 的 `canvasesOnNewPipeline`，挂一次）：新的一份建好，先把交着的画布声明上去（让着的照 `retryOnNewPipeline`
  定再不再试），再在同一下告诉每一方（`Listener.onRebuilt`）照自己的规矩再登记 —— 超级镜子再对一次（看得见、没贴边、亮着屏才登记），
  盲区画面挂着窗口、亮着屏的再对一次 —— 新的一份第一轮就都带着，不用随后再改一次输出。没人用的（超级镜子贴边、熄屏，主界面在后台）照样先声明上去，
  没人登记就不进会话。主界面换管线时把界面的回调接到新的一份上，那一半是它自己的。

## 6. 保活

**定义（2026-09-27）：在不正常的状态下，用各种手段让进程尽量活着，这样接着录的概率更大。**
保活负责「让我们的代码有机会运行」，开机自启动负责「运行起来之后恢复什么」（§2.5）。

- 所有保活手段都归「开机自启动」一个开关管（2026-10-08 并入）。开关关 = 被杀了不回来。录像期间的前台服务照常有，那是录像本身需要的，
  不算保活（§3.5）。
- **能力拉满，但每一种手段都要实机验证有效才算数**；无效的删掉。
- 保活管进程，不管车机睡不睡：深睡不杀进程（睡前睡后 pid 一样），所以保活对「睡着了录不了」没用。

| 手段 | 实测 | 处理 |
|---|---|---|
| 前台服务 | 有效：26 小时、多次深睡，进程一次没被杀（平台笔记 §3.6）。挡不住车机下电：前台服务开着，进程照样在安卓熄屏（下电）后 3–5 秒被结束或者冻住 | 留 |
| 最早启动的 ContentProvider | 有效：进程一起来就先跑到它 | 留 |
| WorkManager 15 分钟任务 | 有效：睡醒 1 秒内必跑；车机重启后也会把进程拉起来 | 留，它同时是「睡醒」钩子 |
| 系统对 START_STICKY 服务的重启 | 没见过（黑匣子专门记它，一次都没出现） | 留着，看 |
| 静态广播拉起 | 有拉起，但不知道是哪几种：黑匣子「起因」记不下真正的拉起者 | 2026-11-10 删掉安卓 8 以后系统根本送不到的（项目所有者），留下送得到的十几种（平台笔记 §3.7）；还是先记真正拉起者，再删没用的 |
| 无障碍服务 | 没试过：要用户去系统设置里打开 | 留（项目所有者 2026-09-27），实机试：开了之后看黑匣子有没有「无障碍服务已连接到系统」 |
| AlarmManager 定时 | 没用过 | 试 |

- 被杀、从最近任务划掉后自己拉自己、系统的 START_STICKY 重启，都只在「开机自启动」开着时做；超级镜子、盲区画面、悬浮按钮、后台录制几个服务的
  sticky 也跟这一个开关。TIME_TICK、静态广播、无障碍心跳只在前台服务不在时才去请相机管家起它（§3.5）；冷启动的恢复（`Recovery.restore`）
  只在 `onStartCommand` 跑一次。

## 7. 诊断

诊断只读、只写记录，不动相机、不改行为。规矩：**一件事一行**，等的那一种只在原因变了时写，绝不每一轮都写；句子在代码里，这里只列要看的几样。

**黑匣子**（`BlackBox`，跨进程留着）：

- **生死时间线**：进程、服务、界面的起停；每一次进程起来的起因和拉起者；心跳（在不在录、录像的样子、`screenOn=` 屏幕真黑没黑、`android=` 安卓
  可交互，变了才写）。
- **屏幕**：每一条边一行（熄屏、车机要睡、车机醒着屏幕黑着、亮屏，带两项车辆信号和安卓的样子）；车没通电时屏幕亮了那一段的起止；
  车辆信号连接每变一次一行；一条边做到一半出错一行。熄屏后的每一步带「，熄屏后 +Nms」（从屏幕真黑那一刻算），安卓也熄屏了再带
  「、安卓熄屏起 +Nms」—— 车机要睡那几步赶没赶在进程没了之前，对着「车机要睡」那一行看。
- **相机管家**：登记表每变一次一行；录像意图开、停（原因、这一段录了多久、有一路在录多久）、自动接回（第几次）、额度用完；「这一趟要录」立、撤、
  接回；黑着时来的「要录」不开的那一行（只在「这一趟要录」真的变了时写）；环视留不留每变一次一行。
- **通道**：「通道：」开头 —— 开（开之前等录像输出）、开不起来、改输出、摘死输出、关、收尾、保持、等、救、车机要睡、退出；「按次序开相机：…」「关相机：…」
  一轮一行，末尾带走了哪些留着的输出、留了多久；每关一路一行「关相机小结」（这一次开了多久、重配几次、各为什么）。改输出、开、救那一行带着这段时间里
  别的在出画面的几路最长断帧多久、会话动没动过。开一路那一下一行「开 X 时的情形」（哨兵模式、车辆信号多久前变过、主界面在不在前、相机服务最后一句、
  我们上一次关它、车机拿过它多久、环视是车机重新初始化后第几次打开）。
- **争用**：别的程序拿走、放开、断开我们的相机，判定一行、放开一行；环视开着时别的程序拿走另一路，30 秒后量一次环视。
- **录像每一路**：每变一次一行 —— 录制器建好了 / 沿用 / 建不起来；加入（出画面到开录多久）、写进第一笔；退出（为什么、文件、录制器怎样了、
  别的在录的几路最长断帧多久）；会话带不上录像输出（连着第几次）；开录落定；一路都不在录了、又有一路在录了、各路都停手了；录像输出摘掉了 /
  随相机关了、录制器放掉（停放了多久）。车上核对「放开之后单独接回、别的路没被动到」看这几行。
- **关座舱时环视**：关座舱时环视开着的，关完那一刻、1 秒、30 秒各量一次环视（最后一帧在关完前多久、断帧、失败 / 丢缓冲）；
  关座舱前先关环视的那一趟一行（环视断了多久）。
- **座舱卡住**：15 秒没出画面那一行带配好以来相机回了什么（`SessionCounts.classify`：HAL 一个都没回 / 只回了错误 / 我们的输出接不住 / 开始了没结果）；
  关掉一份没出过画面的会话时同样写一段。这一步里出了事的开、改输出、救也写一行。
- **轮次和账本**：一台相机一轮满 60 秒还有开或关没返回一行、返回了一行；相机层的断言一行（§4.5）。

**诊断报告**（设置 → 系统 → 诊断信息，导出一份文件）：

- 「2.3 卡顿监测」：后视镜、录制卡住时自动留下的现场（最近 5 份，每一份连同它后面的恢复那一份）；上一次进程怎么退出的、上一次运行有没有崩溃。
- 「2.3.1 相机可用性」：相机服务眼里每一台此刻怎样。
- 「2.3.2 通道调度」：读调度每一轮最后记下的那一份快照（`ChannelScheduler.snapshot()`，不碰调度的账、不建管线）—— 登记表、亮熄屏、前台服务、
  能不能用相机、手上那一步、在等什么；逐路：在出画面 / 在起来 / 被拿着 / 在救 / 停手了 / 没在用，该开（为谁）还是不该开，会话里的输出分要的、留着的、
  死的（`ChannelRules.outState`），这一台的一轮，相机服务最后一句，最近一次开不起来、丢了，救援梯子，来历（车机重新初始化以来开过几台）。
- 「2.3.3 相机步骤统计」（项目所有者 2026-10-14）：调度每结束一步记一条（`StepLog`、`StepStats`，存在应用目录、最近 200 条、跨进程），
  按相机、动作数几次、出画面、没画面、出错、关的用时；再按哨兵、主界面在不在前、离上一次关多久、是不是车机刚放开它、环视是不是第一台分开数；
  关座舱时环视断没断、关座舱前先关环视之后开回来，各一组。
- 「3.1 熄屏（物理屏幕）」：此刻黑没黑、从什么时候起、谁判的，两项车辆信号、车辆接口、安卓可交互、车机要睡从什么时候起、屏幕此刻知不知道。
- 「6.2 车辆信号」：车辆接口、谁登记着、点火、屏幕电源事件、哨兵模式、挡位、车速。
- 「2.6 黑匣子」整段、「9.1 应用记下的警告和错误」（重启后也在，最近 150 条）。
- 每一台相机的来历（`CameraHistory`，跨进程）：相机服务每交给我们一台设备数一台，车机重新初始化它就从头数。

## 8. 实测约束和没解决的

**实测约束**（平台笔记 §3.6）：

- **车机真正重启之后，开机广播送不到我们**（2026-09-27 确认，三个样本）。平时停车是深睡，进程不死，回到车上 App 一直在 —— 这是绝大多数情况。
  真正重启很少见，但重启后进程会被别的东西拉起（WorkManager 的任务还是哪个静态广播，黑匣子记不下来）。所以「车机启动后」这一半不靠开机广播，
  靠这些拉起和「车机重启过」检测（`BlackBox.rebootedSinceLastRun`）。黑匣子另记「拉起者」；恢复本身还待改。
- **深睡醒来收不到亮屏广播**，但能靠深睡时长的增量和醒来后必跑的保活任务察觉（§2.5「什么算恢复」的「能确定」）。

**待项目所有者定的**：

| 事 | 现在 | 要定的 |
|---|---|---|
| 会话配不上时超级镜子让不让（相机管家 3c，2026-11-10 记下） | 不在录像时不丢超级镜子，同一组再试 3 次后交给救援；录像时会丢 | 要不要统一成一条 |
| 让了之后什么时候再试（同上） | 盲区画面、超级镜子、录像、拍照各自一套时机，原样搬进了相机管家（§3.4） | 要不要统一成一条（例如这一路有画面离开会话、这一路重新打开或亮屏时都再试一次） |
| MediaRecorder 模式（不是默认）一路加入时的文件名 | 文件名在备好时就定了，可能比第一帧早几十秒，回放里排得偏早（编码录制不受影响） | 做不做（要先用临时名、开录后改名） |
| MediaRecorder 模式停录 | 停录时放掉录像输出，会话里的输出死了，调度事后摘 | 要不要改成先由调度摘掉录像输出、再停 MediaRecorder（文件晚收尾一步） |
| 车机下电之前能不能早点知道 | 照安卓熄屏判（项目所有者 2026-10-12 D3，接受最后约 15 秒丢掉） | 等更多样本；找到更早、更准的信号只换 `ChannelRules.headUnitSleeps` 一处 |
| 车机放开后座舱之后马上开它（亮屏接回后座舱） | 实车上见过第一次开 15 秒没画面、救援重开才好 | 开的次序、放开之后的安静时间要不要改 |
| 环视被挡着（BLOCKED） | 只算同一次交接 | 看「争用：…之后 30 秒」那一行再定 |
| 降级时熄屏那一轮环视关得慢 | 车辆信号读不到时熄屏就是车机要睡，环视、座舱一起按次序关 | 要不要给熄屏那一轮单设上限 |
| 时间上的改动（项目所有者 2026-10-14 没放进去，各自单独谈） | 一样都不做：哨兵开着时开座舱多等、车机醒来那一下算不安静、15 秒判没画面改短、后座舱黑着时先开前座舱 | 各自单独谈 |
| 出过画面又卡住的环视，救援第一次的重建总失败（实车 3 次全败） | 照梯子来 | 跳过那一次总失败的重建是一个方向 |
| 装新版后第一次开环视没画面 | 只记录（黑匣子写「这一版装好 X 秒后第一次运行」） | 按测试 T1 / T2 分清是装新版的事还是相机回来之后的状态 |
| 回放：离哪一条环视录制都超过一个分段时长的座舱文件 | 不归任何一条，回放里删不掉、锁不到，只由循环清理收 | 单独给它们一条，还是不限距离挂到最近的那一条 |
| 「能用相机」只认主界面在前 | 开机自启动关着时在回放这类我们自己的别的界面里用悬浮按钮开录，会把主界面拉到前面（回放界面随之关掉） | 已知代价 |
| 人在车里、屏幕黑着（露营、小憩）；人在车里、车没通电时点亮屏幕 | 30 秒后同样放开、不录；点亮屏幕照黑着算，按录制键不开、不提示 | 以后可能调整（项目所有者 2026-10-27 先这样） |
| 无障碍服务 | 没人开过 | 实机试过再定去留（§6） |

**以后的方向**（2026-10-09 记下；项目所有者：先用现在的开关逻辑尽量轻量地解决）：车机里的几路相机多半共用一套采集通道 —— 有一路开或关，
车机就要重新安排它。从数据看出来的规矩：一次只动一路；环视单独动；能不动就不动；上一步动完再动下一步。「一个通道调度」（§4）已经做到。还没做的两步：

1. **相机跟着 App 走**：打开 App 开一次，退出、熄屏、关掉主界面才关；最小化、进诊断 / 回看、悬浮按钮拍照都不动通道。代价：内存和主界面开着时一样
   （约 80–120 MB 图形缓冲）；耗电是相机和车机的 360 拼接在最小化时继续跑；后台拿着相机要前台服务。要改项目所有者定的「谁在用，都不用了才释放」。
   现在的「保持 30 秒」「每一路各自保持」「管线属于应用」是它的轻量版。
2. **每路只开一个固定输出**（项目所有者 2026-10-10 记下，这次不做）：开着时永远不变，预览、超级镜子、录像由我们自己用 GPU 分画面；开着时通道一次都不动，
   只剩「打开、关闭」两步。代价：每路每帧多一次 GPU 拷贝、多几十 MB 显存、略多耗电。现在的做法不堵这条路：输出的主人只声明，相机层只按计划建会话，
   消费者只在离开会话之后才放。
